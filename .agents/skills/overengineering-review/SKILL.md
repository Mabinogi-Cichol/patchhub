# 过度设计审阅

目标是识别超出实际需求和必要约束的设计复杂度，给出保留业务需求的最小修改建议；过度防御是重点检查项之一。

## 依据与范围

读取目标仓库的 AGENTS.md 及目标目录适用规则，重点应用其中有关精简设计与防御性逻辑的要求；以目标仓库为准，不将技能所在仓库的规则套用到其他项目。仓库没有相关规则时，按用户明确需求及下述判断方法审阅，不要求为此新增规则文件。用户当前明确需求决定审阅范围。

按用户请求选择计划审阅、实现审阅或二者对照。目标可为文档、对话方案、提交、分支差异、未提交改动或指定模块；优先沿用对话中明确的功能及范围。只补读判断所必需的关联材料；范围无法确定且会影响结论时询问目标，不自行扩展为全仓库审计。

默认输出审阅意见。用户已要求修改计划或修复代码时，直接在授权范围内处理并说明变更；仅审阅不自动修改代码、提交、发布或操作设备。

## 共用判断方法

先明确实际需求、成功路径及已有约束，再沿方案或实现中的关键流程判断相关机制是否必要。关注限制、校验、超时、重试、兜底、恢复状态、抽象和配置，但不要求方案或实现逐项增加这些机制。

对可疑策略追溯其理由：

- 它解决了什么已遇到的问题，或防止什么有明确依据、会阻断正常流程的故障？依据可以是复现记录、现有代码行为、接口契约或明确的运行约束；不要求所有问题都先在线上发生。
- 触发条件是什么，会怎样影响正常流程？策略是否实际解决该问题，还是只拒绝合法输入、截断输出、隐藏错误或转移失败位置？
- 删除该机制后，当前需求或必要边界是否仍然成立？能否用更直接的处理方式解决同一个实际问题？

沿成功、失败及实际涉及的取消或恢复路径检查是否能到达明确结果。指出有证据的不可达分支、循环重试、无法退出的状态和错误被吞掉后仍继续执行的路径；不要为了检查这些路径而要求新增状态机。

## 计划审阅

从需求到实施拆分检查策略是否必要、流程是否能闭合。对尚未实现的内容只评价方案，不将计划描述当作代码行为或完成证据。

## 实现审阅

先确认审阅基线与实际改动范围，读取相关 diff 和完整函数，并按需追踪调用方、被调用方、配置及测试。用户要求审阅某个已完成功能时，检查其实际实现，不能仅凭工作区没有 diff 判定没有问题。

- 从业务入口沿输入处理、执行、结果生成和错误传播追踪真实路径，核实限制是否生效、重复校验是否确由内部契约覆盖、超时是否误杀正常任务，以及兜底或状态恢复是否隐藏失败或阻断后续流程。关键词搜索只用于定位，不作为发现的充分证据。
- 有设计或计划时，对照实现是否自行新增了限制和防御分支、是否保留了已决定删除的机制。即使代码与计划一致，仍需按当前仓库原则判断；计划中的不合理策略不能成为实现合理性的依据。没有设计文档时依据明确需求和代码审阅，不为此额外要求补写文档。
- 对每项发现提供具体触发条件、实际调用或状态路径及影响。未复现时明确这是静态分析；必要且可行时运行针对性验证。沿用已有有效验证记录，只有新增修改、失败或未解决问题才补充检查，不把施工记录或测试通过当作原则已落实的证明。
- 检查建议删除的机制所关联的配置、错误提示、专属测试和残留分支；保留仍验证业务契约的测试。区分本次引入的问题与相关的既有问题，不把无关旧代码扩展进修复范围。

## 判断尺度

- 区分“确认无依据或不必要”和“目前材料不足”。先利用已有材料核实；无法确定的写为待核实项，不把缺少描述当成策略必然错误，也不要求通过增加防御代码来补齐证据。
- 有依据且必要的策略应保留。不得机械删除所有校验、超时或安全边界，也不得以减少行数牺牲需求和正确性。
- 确认无依据的限制应建议删除，并指出相关配置、错误分支和专属测试的清理范围；不以调大阈值替代删除。
- 建议本身也须符合精简原则。不要默认用流式处理、队列、重试框架或新的配置层替换一个本来可以直接删除的检查。
- 不为凑问题数量制造发现，不作泛化加固建议，不将个人风格偏好当作缺陷。不设置审阅问题数量、报告长度或审阅耗时的任意上限。

## 输出

先给出结论：未发现需修改项、建议修改，或关键依据待核实。说明本次审阅对象、代码基线（如适用）和实际覆盖范围。静态判断、已执行验证及未验证项应区分；结论不代表未执行的测试或实机验收已通过。

有问题时，按实际影响排序，每项说明：

- 位置：计划文件与章节或行号；对话方案引用具体条目；代码发现给出文件与准确行号，并说明必要的调用关系。
- 依据与影响：对应的需求、规则或事实，以及为何造成无用复杂度或阻断正常流程。
- 最小建议：明确保留、删除或简化什么，并说明如何保持原需求。

将待核实项与已确认问题分开，只列会影响判断的信息及可行的核实方式。没有发现时简短说明通过及审阅范围，不强行生成问题清单或冗长报告。

# Steam 游戏补丁管理工具：调研与开发计划

调研日期：2026-09-30。此文档保留开发前方案；制定时仓库没有应用代码或提交历史。本计划中的技术选型、规模和工期均为建议，不表示已完成实现。2026-10-01 已开始 P0 首批实现，实际交付与未完成事项见 [进度记录](progress.md)。

## 1. 产品目标与边界

面向需要额外内容补丁的 Steam 游戏玩家，提供“扫描已安装游戏 → 自动匹配补丁 → 查看兼容性与当前状态 → 安装 → 检测 / 更新 / 卸载”的完整流程。

目标平台分为 Windows 独立桌面应用，以及 SteamOS 游戏模式中的 Decky 插件。Windows 首版建议支持 Windows 11 x64；SteamOS 首先验证 Steam Deck x86_64。其他 Linux 发行版和掌机不作为首版承诺。

“所有游戏”指当前机器上可访问、已挂载 Steam 库中的游戏安装实例，包含没有已知补丁的游戏；不是账号拥有但未安装的游戏。工具、运行时、DLC 和下载中的项目需要识别或单独归类，不静默当成完整安装游戏。

自动匹配不等于全网补丁覆盖，也不等于后台自动修改游戏。用户看到来源、补丁版本、兼容条件和文件变更后触发安装。目录中没有记录时显示“目录暂无匹配”，而不是“此游戏不需要补丁”。

首版默认只接入发行商 / 开发者官方发布的内容恢复补丁。汉化、去码、社区 Mod 等可作为后续独立类别；不同类别可能冲突，不能都标为“完整内容补丁”。付费 DLC 应引导 Steam 正规获取流程，不冒充文件补丁。

## 2. 调研结论与证据限制

1. HGamer 可以作为发行商与补丁线索入口。本次读取的[补丁资源库](https://hgamer.tw/zh-TW/patches)快照显示 653 条记录与类型 / 语言筛选；不能据此保证覆盖全部游戏。直接读取用户给出的 publishers 页失败，因此尚不能声称已完整读取发行商清单。入口见 [发行商页](https://hgamer.tw/zh-TW/publishers)。公开 API、抓取许可、再分发许可仍需分别核实。
2. 补丁发现、补丁获取、补丁安装是三个不同问题。网页有下载链接，仍可能存在年龄确认、登录、网盘跳转、EXE 安装器、区域或版本限制。每个来源都必须配置能力等级。
3. Steam 本地库文件是安装发现的主要依据；其结构需要实际客户端样本回归验证，不应当作长期稳定的公共 API。无需让用户提供 Steam 密码或 Web API Key。
4. Decky 提供独立插件宿主与模板；适合掌机入口，但需要独立 UI 与生命周期适配，不能直接装 Windows UI。见 [Decky Loader](https://github.com/SteamDeckHomebrew/decky-loader) 和 [插件模板](https://github.com/SteamDeckHomebrew/decky-plugin-template)。
5. Proton 为 Windows 游戏提供 Linux 运行支持；这不证明每一个 Windows 补丁安装器可运行。首版直接操作游戏文件，EXE 安装器自动化进入后续验证范围。见 [Valve Proton](https://github.com/ValveSoftware/Proton)。

具体来源证据与尚未验证的事项在 [research-sources.md](research-sources.md) 中维护。

实际样本体现了三种接入模式：Dharker 的 Negligee 官方说明是向 game 目录加入 adultpatch.rpa，适合验证新增文件配方；Paper / Dischan 的 Mahou Arms 使用会自行匹配版本的 patcher，且公开说明有 Deck 用 Linux 版本，首版应引导官方程序；HGamer 的 072 Project 样本说明要求会员免费结账后下载，适合浏览器获取后导入。这些是候选案例，尚未审核文件或验证自动安装，链接与证据见来源文档。

特别注意，072 Project 的该样本页面描述的是修复事件与 BUG 的更新补丁，不能直接当成成人内容恢复补丁。门户“补丁”分类本身不足以确认产品目标，必须审核每个条目的用途。

## 3. MVP 能力

| 功能 | 首版行为 | 不满足条件时 |
| --- | --- | --- |
| 游戏扫描 | 自动识别 Steam 根目录、多库、多磁盘和已挂载 SD 卡；可手工添加 Steam 库 | 给出不可访问 / 未挂载 / 清单损坏诊断 |
| 补丁匹配 | 用 AppID 精确匹配目录，按平台、语言、渠道、版本过滤 | 模糊名称仅作线索，不允许直接安装 |
| 状态检测 | 校验补丁特征文件与安装事务记录 | 证据不足显示未知或冲突 |
| 自动安装 | 经审核、固定版本、具有完整哈希与明确文件映射的 ZIP 配方 | 提供官方页面和手动获取说明 |
| 本地导入 | 用户选择下载的 ZIP，必须与可信目录哈希一致 | 哈希不一致拒绝托管安装 |
| 更新 / 卸载 | 更新前重新校验；按记录回滚，保护后续修改 | 冲突保留文件并提示处理 |
| 离线使用 | 使用最后一次可信目录与本地记录，显示更新时间 | 无目录时仍能扫描游戏 |
| 双端入口 | Windows 列表与详情；Decky 控制器可操作的列表与确认页 | 不支持的操作显示具体原因 |

建议首版数据目标：2–3 个发行商、10–20 个经过人工核对的 AppID，其中至少 5 款完成 Windows 与 Steam Deck 实机安装 / 回滚验证。该数量是验收目标，必须在 P0 样本核查后调整，不能提前保证可获得这些补丁。

首版不实现任意远程脚本、通用 EXE / MSI 执行、破解或付费内容解锁、账户凭证托管、补丁文件镜像分发、云端游戏库同步以及全量自动爬虫。

## 4. 交互流程

首次启动：说明内容类型与来源 → 扫描本地 Steam 库 → 同步补丁目录 → 展示所有已安装游戏。成人内容提示与必要的来源年龄确认保留，具体地区要求在发行前核实。

游戏列表至少显示名称、安装库、匹配补丁、安装状态、平台兼容性；支持“全部 / 有补丁 / 已安装 / 需处理”筛选。详情页显示来源链接、发行商、补丁版本、适用游戏版本、语言、大小、检测时间与依据。

安装页展示将新增 / 覆盖 / 删除的文件数量、备份空间、冲突与已验证平台；按下安装后显示可取消的下载与准备阶段。提交阶段不能随意中止，改为完成或回滚后报告结果。若来源要求浏览器获取，返回工具后导入文件并继续同一流程。

Decky 首版以插件内部列表为稳定入口；游戏详情页快捷入口作为后续增强，避免 MVP 强依赖 Steam 私有 UI 注入。按键焦点、长标题、滚动、触屏、返回键和下载后后台恢复均需实机验证。

## 5. 技术架构与选择

来源能力核心化的具体迁移拆分见[独立设计](features/shared-source-discovery/design.md)与[施工记录](features/shared-source-discovery/progress.md)，当前为迁移方案、待实现；Windows 接入与验收先于 Decky 切换。

建议采用共享 Rust 核心，负责 Steam 库解析、匹配、指纹、下载验证、文件事务、恢复和 SQLite 存储。Windows 使用 Tauri 2 + React / TypeScript；SteamOS 使用 Decky React / TypeScript 前端 + Python 桥接后端，再调用随插件打包的 Linux 核心进程。

Windows 可以直接链接核心库；Decky 桥接通过 stdin/stdout 上的版本化 JSON 消息调用核心，无监听公网或本地 TCP 服务。Python 仅转换 Decky 调用和任务事件，不复制安装逻辑。UI 共享 DTO、状态文案和业务 hooks，视觉组件按平台分别实现。

```text
签名补丁目录 ──→ 本地可信目录缓存
                       ↓
Windows Tauri UI → Rust commands ┐
                                ├→ Rust 核心 → Steam 库 / 游戏文件
Decky UI → Python bridge → CLI ┘       ↓
                              SQLite / 事务日志 / 备份
```

这一路线增加 Rust 与 Python 的打包工作，但能保持跨平台安装规则和安全检查一致。备选方案是 Python 共享核心配 Windows 桌面壳，初始开发更快，代价是运行时分发与双端权限管理复杂。P0 用同一个配方做双端验证后再正式锁定 Rust 路线。

Tauri 的 capabilities 可控制前端权限，但核心自己的路径检查仍然必要；远程网页应在外部浏览器打开，不能获得本地 IPC 权限。见 [Tauri capabilities](https://v2.tauri.app/security/capabilities/)。

建议仓库结构：

```text
apps/windows/              Tauri 桌面应用
apps/decky/                Decky 前端与 Python 桥接
crates/core/               库发现、匹配、事务安装
crates/cli/                Decky 所用 JSON 协议入口
packages/contracts/        DTO / JSON Schema
catalog/                   人工审核的发行商与补丁元数据
tools/catalog/             来源检查与目录发布工具
tests/fixtures/            合成 Steam 清单 / 压缩包 / 游戏目录
docs/                      方案、支持矩阵与运营流程
```

## 6. Steam 游戏发现与匹配

Windows：优先从当前用户 Steam 注册表位置和常见安装路径发现根目录，允许用户指定；SteamOS：检查 deck 用户的 Steam 目录及其实际指向。候选路径只用于发现，之后读取 libraryfolders.vdf 枚举库，在各库 steamapps 中解析 appmanifest_<appid>.acf。

解析器必须理解 Valve KeyValues 的引号、转义和嵌套，而不是用正则截取。支持新旧库结构；用 appid、name、installdir、buildid 与可用状态字段生成实例。检查实际目录存在、库挂载状态和未完成下载，单个损坏清单不影响其他库扫描。

不能把所有目录名都当游戏，也不能因为 ACF 存在就确认安装完整。工具 / 运行时分类需要额外元数据；无法确定时保留“类型未知”，不从总览消失。账号切换时重新扫描，扫描结果不作为所有权证明。

安装实例标识包含 AppID + 本地库标识 + 安装路径；同一 AppID 的多个实例独立管理，库移动后重新识别并请求确认记录迁移。只对匹配的实例读取少量检测文件，避免全库哈希。

匹配优先级：AppID 精确匹配 → 平台与渠道 → 语言 / 补丁类别 → buildid 与基线文件指纹。buildid 是兼容条件的一部分，不等于发行商的语义版本；已验证兼容范围以目录显式记录为准。未知的新 build 默认暂停自动安装，先提示待验证。

SteamOS 下文件覆盖补丁通常指向游戏目录，不直接放入 Proton prefix。依赖注册表、DLL override、安装器或 prefix 的补丁要单独配方与实机验证。Linux 大小写、符号链接、权限、SD 卡卸载都需要处理；Windows 能用的配方不可自动标为 Deck 兼容。

## 7. 补丁目录与来源策略

### 7.1 分层接入

HGamer 用于发现发行商与详情线索；发行商官方页面作为发布证据；审核后的补丁目录才是客户端的匹配依据。首版不要求客户端实时遍历所有发行商网站。

每个来源支持级别：`discover_only`（只给链接）、`manual_download`（浏览器下载后哈希校验导入）、`managed_zip`（可信配方自动下载安装）、`unsupported`（已知不支持）。同一发行商可以同时包含不同级别。

来源适配器输出候选条目，不能直接生成可执行安装动作。维护者核对 AppID、下载来源、语言、版本、安装说明、哈希和平台后，才进入发布目录。网页解析失败应保留最后可信条目并标记过期，不能静默产生空目录。

客户端获取静态签名目录即可，初期无需商业服务端。来源采集在维护端低频运行，遵守访问规则、限流与授权。robots.txt 不等于再分发许可；没有明确授权时只发布必要元数据与原始链接，不托管补丁正文或文件。

### 7.2 数据模型

| 实体 | 必备字段 |
| --- | --- |
| GameInstall | instance_id、appid、library_id、install_path、buildid、availability |
| Publisher / Source | id、official_url、discovery_url、support_level、last_checked_at |
| PatchRelease | patch_id、release_id、appid、category、language、version、platforms、source_page、artifacts、compatibility、recipe、detection、conflicts |
| Artifact | approved_url / manual 来源、sha256、size、archive_type、allowed_redirect_hosts |
| Recipe | schema_version、固定文件映射、基线条件、新增 / 替换 / 明确删除列表 |
| Detection | 必需文件、版本对应 sha256、可选辅助标记、证据强度 |
| InstallTransaction | instance_id、release_id、状态、每文件前后哈希、备份位置、journal、时间 |

目录带 schema_version、递增 revision、生成与过期时间、签名和签名 key_id。内置可信公钥，定义密钥轮换与撤销流程；拒绝降级到旧 revision。文件哈希只能证明和审核版本一致，不能单独证明文件无害。

发布流程：候选发现 → 人工核对 → 获取授权条件 → 在受控测试环境校验文件与行为 → 配方测试 → 双端兼容声明 → 签名发布。记录核验人、时间和测试 build；有风险时可撤销版本并阻止新安装。

## 8. 安装状态不是单一布尔值

三个独立维度：游戏是否可访问、目录是否匹配、补丁是否被检测到；下载 / 安装任务状态单独显示。

| 补丁状态 | 判断与操作 |
| --- | --- |
| 未检测到 | 已运行可信规则且标志缺失，允许兼容性检查后安装 |
| 已安装 / 托管 | 文件指纹与当前版本一致，且有本工具事务记录 |
| 已安装 / 外部 | 文件指纹一致，但没有本工具备份；不可承诺还原原版 |
| 部分安装 / 冲突 | 部分特征存在、哈希不符或多个补丁争用文件；阻止直接覆盖 |
| 需重新验证 | 游戏 build 或文件变化，原兼容声明失效 |
| 可更新 | 当前补丁可信检测成立，且存在已兼容的新版本 |
| 状态未知 | 没有足够检测规则、访问失败或未知外部修改 |

“目录暂无匹配”属于匹配状态，不能推导“未安装”。“已安装”只证明文件条件，不证明游戏内内容体验正确；平台运行验证另列为已验证 / 未验证 / 不支持。

## 9. 可恢复安装与卸载

事务流程：`planned → downloading → verified → staged → backed_up → applying → validating → committed`；异常进入 `rolling_back`，之后 `rolled_back` 或 `needs_recovery`。整个任务采用每安装实例独占锁，事务日志先于对应文件变更落盘。

1. 预检：重新解析目标实例，验证游戏版本 / 文件基线、可写权限、运行或更新迹象、磁盘空间、配方冲突。不能可靠确认安全时要求关闭游戏 / 暂停 Steam 更新后重试；进程检测不是绝对保证，提交前再次校验文件。
2. 获取：HTTPS、有限重试、取消、大小上限；临时文件保留 .partial 后缀。响应是 HTML / 登录页或重定向到未批准主机时停止。带签名的短期下载 URL 需维护端更新或退回手动导入。
3. 校验与准备：检查可信目录签名、完整 SHA-256 和包大小，在隔离暂存目录解压，只保留配方允许的文件。
4. 路径检查：拒绝绝对路径、..、驱动器 / UNC、NTFS ADS、设备名、路径穿越、符号 / 硬链接、reparse point 越界，以及大小写碰撞、重复条目、超限展开与压缩炸弹。读取与写入路径分别验证；尽量使用安全句柄防止检查后换链。
5. 备份：覆盖文件先复制并核验原哈希，新增文件记为此前不存在，删除仅限明确批准的文件。绝不批量备份后任意覆盖目录；存档 / 配置默认不写。
6. 提交：每文件在目标文件系统暂存再替换，记录进度并校验最终哈希。跨文件提交不是全局原子操作，依靠持久 journal 在崩溃后恢复。
7. 卸载 / 回滚：仅当当前文件仍等于本次安装结果时恢复备份或删除新增文件；有新修改则保留并报告冲突。Steam 更新后旧备份可能不再对应现版本，禁止无条件恢复。

补丁更新需要迁移事务：保留原始游戏备份与各次变更链，不能把旧补丁文件作为“原版备份”。若基础游戏已更新，重新获得经过验证的干净基线再安装。首版限制同一实例单一托管内容补丁，多 Mod 叠加后续实现。

Windows 普通用户运行，受保护目录写入不足时给出库迁移或后续最小权限 helper 的明确操作；首版不让整个 UI 常驻管理员。Decky 宿主权限必须实机检查，核心尽可能以游戏文件所属用户运行，不能因为宿主高权限而放宽边界。

## 10. 核心接口与错误处理

拟定接口：`scan_libraries`、`list_installs`、`match_patches`、`detect_patch`、`plan_install`、`start_install`、`get_task`、`cancel_task`、`plan_uninstall`、`start_uninstall`、`recover_transactions`。

`plan_install` 返回实例、目录 revision、基线指纹、目标 release、变更列表、空间和冲突；`start_install` 只接受短期 plan_id，并重新确认基线，前端不能传入任意目的路径或 shell 命令。IPC 带 protocol_version、request_id、task_id，限制消息长度，stdout 只输出协议消息，诊断走 stderr。

稳定错误码至少包含：库离线、清单损坏、版本不兼容、检测不确定、下载失效、哈希不符、路径非法、空间不足、无权限、游戏忙、文件变化、恢复冲突。UI 提供明确恢复动作，不将所有失败合并成“安装失败”。

工期估算基于 1 名熟悉 Rust / TypeScript 的全职开发者，能够借用 Steam Deck 与合法游戏样本；按有效工作周计算，外部授权 / 插件审核等待不计入。建议 8–12 周，样本获取或兼容问题可能扩大范围。

| P0 可行性 | 第 1–2 周 | Steam 双端样本解析；发行商样本矩阵；同配方 CLI 安装 / 回滚；Decky 调用核心 PoC | 至少 3 个真实补丁确认包结构与许可条件，至少 1 款双端闭环；否则调整 MVP |

| P2 Windows Alpha | 第 5–6 周 | Tauri 列表、详情、下载导入、确认、进度、卸载 | 多库实机扫描与 5 款经过审核游戏闭环；所有状态可解释 |

Decky 商店可接受性与成人相关插件规则列为 P0 独立询证项；不能把技术可打包等同于一定能上架。开发 / 测试 ZIP 分发按 Decky 官方流程实施，商店提交另设外部门槛。

首轮可执行任务顺序：

1. 收集 Windows 多库、Steam Deck 内置盘 / SD 卡的脱敏清单，建立发现 fixtures。
2. 人工核对 HGamer 发行商页，选 3 个候选来源，填写来源证据矩阵；只承诺实际核验过的能力。
3. 选择 3 个代表样本：纯覆盖 ZIP、包装层级复杂 ZIP、需浏览器获取或 EXE 的引导样本。
4. 固定 GameInstall / PatchRelease / InstallTransaction Schema 和状态语义。
5. 实现 CLI 最小扫描、安装计划、备份与回滚，再接入双端 UI。

## 12. 验证方案与指标

| 类别 | 必测情形 | 验收依据 |
| --- | --- | --- |
| 库发现 | 多盘、中文 / 空格路径、旧新版 VDF、损坏 ACF、重复 AppID、未完成下载、SD 卡离线 | 已挂载测试库完整列出；单条错误不导致全局失败 |
| 匹配 | 相同标题不同 AppID、Demo / 正式版、渠道 / 语言不符、未知 build | 测试矩阵内无错误自动安装匹配 |
| 检测 | 原版、托管、外部安装、部分文件、Steam 覆盖、未知版本 | 每种状态有真实文件证据与对应动作 |
| 文件安全 | Zip Slip、链接、ADS、大小写重复、压缩炸弹、重定向 HTML、哈希篡改 | 均在写游戏文件前拒绝 |
| 恢复 | 下载 / 备份 / 每文件替换时故障、进程被杀、满盘、取消、SD 卡拔出 | 重启可恢复；不误删存档与后续修改 |
| 更新卸载 | v1→v2→卸载、Steam 更新后卸载、冲突 Mod | 只恢复适用基线；不盲目覆盖新游戏文件 |
| 双端运行 | 同一补丁 Windows / Proton、插件重载、控制器焦点、缺少 prefix | 文件安装和游戏运行结果分开记录 |

性能目标初稿：500 个清单的本地扫描 ≤5 秒（参考设备、冷 / 热缓存分别记录）；游戏列表首屏不等网络；只对命中补丁运行指纹，不哈希整库。以上需基准验证后修订。

Beta 指标关注已审核游戏安装成功率、回滚成功率、误匹配数和来源失效率。用户游戏库默认仅存本地；遥测默认关闭，日志脱敏路径、用户名和 URL token，不上传成人游戏拥有信息。

## 13. 主要风险与决策

| 风险 | 处理策略 |
| --- | --- |
| 站点没有稳定 API 或授权 | 人工目录先行，抓取是维护辅助；失效可退回官方链接 |
| 补丁覆盖多个版本、说明模糊 | 文件基线与审核 build 限定，未知版本不自动安装 |
| 游戏更新破坏补丁与回滚基线 | build / 文件变化触发重新检测，禁止恢复过期基线 |
| EXE 与 Proton 兼容复杂 | MVP 提供引导；后续为每个已验证安装器设计专用适配 |
| Decky / Steam UI 变化 | 主流程在插件列表；固定验证版本并维护升级矩阵 |
| 恶意目录或补丁供应链 | 签名目录、审核哈希、无远程任意脚本、撤销版本 |
| 自动化卸载删除用户修改 | 安装后哈希守卫、冲突保留、外部安装不可承诺回滚 |

目前采用的规划假设：优先中文界面；首版不镜像补丁文件；先小规模官方内容补丁；双端共享安装核心；Windows 先 Alpha、Decky 随后补齐。后续最影响范围的产品选择是是否纳入社区汉化 / 去码、是否接受付费补丁，以及发行商合作资源；不影响先做库扫描与安装事务 PoC。

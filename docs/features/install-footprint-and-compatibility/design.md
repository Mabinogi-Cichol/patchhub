## 3. 文件生命周期与所有权

符号：D 为下载包（普通 ZIP 或 EXE）；Z 为 EXE 规范化 ZIP 实际字节数（当前 STORED，约 P 加元数据，不能恒等 P）；P 为选中映射输出总大小；O 为被覆盖原文件总大小；p_i/o_i 为单个输出/原文件大小；L 为最大单个工作文件；M 为卷内余量，另计元数据、worker 二进制和文件系统分配开销。

| 材料 | 当前所有者/用途 | 计划释放时点 | 必须保留的情况 |
| --- | --- | --- | --- |
| 下载包 D | 下载缓存；分析/转换输入；重试来源 | 安装终态后按 auto_cleanup；转换成功不提前违反“成功后清理”设置 | 正在消费、重试、用户要求保留缓存 |
| 分析沙箱输入 D 与 runtime | WorkerExecution/InvocationDirectory | 复制出已校验报告、worker 退出后立即释放；移到空间复检之前 | 子进程未退出、输入句柄尚未关闭 |
| 转换沙箱输入 D 与 runtime | 当前与输出共享 InvocationDirectory | worker 退出且产物校验/移交后释放，只保留 artifact 所有权 | 转换仍在运行；Windows ACL/profile 清理未完成 |
| 规范化 ZIP Z | 当前由 converted 对象连同整目录持有 | 旧 stage 路线：prepare 完整完成且以后不再读取产物时；新路线：最后一个消费者/恢复引用解除后 | 新无 stage 事务仍需读取、活动事务仍引用该产物 |
| 完整 stage P | 当前 prepare 写入，每成员一份 | 新计划完全省略；旧计划仅为恢复已有事务保留 | 旧事务必须按旧语义恢复；当前/未写成员仍可能需用 |
| backup O | journal 管理的原文件恢复材料 | 临时恢复路线在提交/回滚终态持久化后清理；持久卸载备份沿用收据保留语义，清理失败单独报告并重试 | needs_recovery/恢复冲突仍依赖；用户显式清理全部备份属于独立功能 |
| 游戏 .tmp | 当前成员写入或恢复暂存 | 校验后同目录 rename；失败先辨明所有权再移除 | 外部修改的未知临时文件不能直接当作本工具垃圾 |
| 报告/journal/收据 | 解析证据、文件映射与重装/恢复所有权 | 按恢复和收据需要保留；删除独立短期授权及续期状态 | 恢复、幂等请求需要的内容摘要与映射并入既有记录 |

成功流程：下载 → 分析（释放分析沙箱）→ 转换（移交 Z、释放转换输入/runtime）→ 只读建计划 → 全量备份 → 逐成员写入 → 持久化终态 → 解除归档引用并释放可清理的 Z/backup → 按设置清下载。取消/失败进入回滚；恢复冲突保留必要 backup 与证据，不能因“阶段结束”就清掉全部材料。进程崩溃不保证 Drop，重启按 owner 标记、活跃锁、journal 引用扫尾；删除失败不把安装成功变成失败。

## 4. 普通 ZIP 省略 stage 的方案

采用“压缩包作为只读载荷来源，逐成员直接解压到游戏同目录临时文件”，不直接边解压边覆盖最终文件。保留当前先备份全部原文件再写入的事务顺序，避免把空间优化同时扩大为事务算法重写。

1. 下载结束核对包摘要，持有已有缓存锁并记录事务对源包的引用（无到期时间、无心跳）。目录预检、路径/编码/重复目标/大小校验及所有成员摘要在只读计划阶段完成，不生成完整 stage。仍需解压读取一次验证；省磁盘不等于省掉全部读取与解码。
2. 计划保存来源类型、压缩包摘要/大小、成员稳定定位（索引加原始名称）、映射、目标摘要、输出大小、原文件事实和所需能力版本。prepare 与 apply 共用成员校验器，避免两层策略漂移。已有签名 ZIP 与动态 ZIP 均纳入，新 EXE 产物也复用。
3. 自动下载引用受管理缓存；外部本地 ZIP 要么可稳定打开并在 apply 保持同一受控句柄，要么复制一次到受管理的内容地址路径。禁止仅持久化任意外部路径，重启后盲信同名文件。跨进程恢复须重新核对摘要和路径身份。
4. 写入前核对目标实例、实际安装条件、载荷和现有目标，完成 backup。每个成员流式写入独占创建的 .tmp，限制到声明长度加一字节并核对长度/CRC/SHA；sync 文件、检查最终目标仍为预期原态、同目录 rename、同步目录，最后记录成员状态。
5. apply 期间用既有缓存锁阻止并发清理，崩溃后由未完成 journal 的引用保护源包。最后一个成员写完也不能仅以循环结束为由删除来源，必须先提交事务并消除临时文件恢复依赖。
6. 崩溃恢复按 journal 的 writing/written/restoring 状态识别：完整临时文件用计划中的目标摘要识别；不完整临时文件可用被固定的 archive 成员流验证前缀（替代现有 stage 前缀比对），无需整份 stage。**若源包缺失，只凭文件名和数据库状态不能安全删除不完整临时文件**；保留并报告具体恢复缺料。可后续补充可信临时文件身份/分块检查点，未完成前不声称源包丢失仍总能自动回滚。
7. 回滚使用 backup；只在确认当前目标属于原态/已安装态时恢复，不覆盖用户外部修改。无 archive 也可恢复不依赖其验证的成员；遇到未知 .tmp 保留。新增文件的清除仍受安装态摘要约束。既有非transient事务若承诺后续卸载，必须保留卸载所需原文件备份；无stage改造不能顺带撤销该承诺，其O属于持续占用而非成功即可释放的临时量。

新计划直接采用无 stage 路线，取消另建“写完逐成员释放 stage”的过渡实现，避免新增状态及恢复分支。已有 stage 事务保留最小读取与恢复兼容，不给新计划提供双模式开关，不在升级时清除旧未完成事务材料。

## 5. 逐阶段、逐卷容量模型

### 5.1 当前预算与问题

- ZIP 下载已存在时仍要求 state=P+O+16 MiB、target=P+O+16 MiB；stage 完成后 state 才扣去 P。同卷合并。实际游戏写入为串行单成员 .tmp，target 对 P 与 O 同时全额预留偏保守，但不能改成只需 L：最终新增文件/体积增长会累积。
- EXE `SpaceBudget::new`：state=2D+2P+O+32 MiB，target=P+O+16 MiB；把 Z 近似成 P。分析后/转换后都对实时空闲使用同一完整预算，重复计入已存在 D、转换输入及 Z；且空间检查在 drop(analysis) 前发生。
- EXE 下载前另有固定 2 GiB+余量门槛，会拒绝实际小包；大文件必须按已知长度或下载过程中剩余空间判断。

### 5.2 新预算计算

按现有下载、分析、转换、安装阶段，用纯计算函数列出每个实际卷上已分配、即将创建、可靠可释放的材料及目标体积变化。下式用于核对容量计算，不要求实现通用材料图、动态调度器或新的材料生命周期状态机。某时刻卷 v 所需额外空闲：

`need(v,t) = max(0, max_future_s[footprint(v,s) - footprint(v,t)]) + margin(v)`

只减去**已经成功释放**或在后续峰值前有确定释放顺序的材料，不把清理失败/稀疏文件/硬链接/压缩收益提前当作可用空间。各实际路径分别查卷 ID（state、worker staging、缓存、游戏根）；同卷聚合一次、不同卷不能拿其他卷空闲抵扣。每个阶段边界复检实际空闲，I/O 的 ENOSPC 仍走正常回滚。优先复用并核实已有锁和串行执行约束；若仍可并发进入安装，先在既有安装入口明确串行。本次不新增卷级预留服务；未来确有并发安装需求再单独设计。检查后空间仍可能被其他程序消耗。

目标卷以安装前真实游戏为基准。固定写入顺序，`delta_k = sum_{j<=k}(p_j-o_j)`；新增文件 o_j=0。写入第 i 个临时文件时增长 `delta_(i-1)+p_i`，rename 后为 delta_i。逆序恢复第 i 个原文件时临时增长 `delta_i+o_i`，恢复后为 delta_(i-1)。因此初始保守精确逻辑上界：

`T = max(0, 所有 delta_k, 所有 delta_(i-1)+p_i, 所有 delta_i+o_i)`

安装前按固定成员顺序计算目标卷峰值，阶段切换时扣除已存在材料；恢复仅依据既有journal状态计算所需空间，不新增持久化容量状态或逐成员预算调度机制。如恢复顺序变化须核对相应计算。restore 与 write 的 .tmp 不会同时存在时取最大值，不把两份总量相加。保留单成员临时文件意味着大文件本身仍需相应空间。分配粒度、journal、目录项、CoW/快照影响不能由逻辑字节严格保证，以现场测量和余量补充。

无 stage 普通 ZIP，包 D 已存在且与 state 同卷：state 新增 O，target 新增 T，分卷各加 M；同卷新增 O+T+M（每卷只计一次余量）。从下载前计算的全过程总临时占用包含 D；包已有时不再额外预留 D。

EXE 在下载/worker/state 同卷且游戏也同卷的简化模型：旧实际材料峰值约 `max(2D+Z, 2D+Z+P+O+T)`，新路线为 `max(2D+Z, D+Z+O+T)`，另计 runtime/元数据/余量。第二阶段减少一份沙箱 D 以及 stage P；下载缓存 D 仍按用户设置保留。转换可能边读 D 边生成 Z，不能预先删除输入。若多卷，逐项分配材料到真实卷，不能直接把此总式用于某一卷。

### 5.3 容量示例（GiB，忽略余量和元数据，非实测）

普通 ZIP：D=1，P=4，四个成员各 1，均新增，O=0。T=4。旧逻辑材料峰值为 D+P+T=9；新路线为 D+T=5。下载已存在时同卷额外空闲需求由旧预算 8 降为 4。若全部替换同样大小原文件，O=4、delta 恒为 0、T=1；新路线仍需 O+T=5，不能省略恢复备份。

EXE：D=1，Z约4，P=4，O=0，T=4。旧峰值约14，新峰值约9；转换阶段约6。原预算在 D 已存在时仍额外要求 state=10、target=4（共14），转换后重复检查更可能拒绝。新预算从当前占用求后续增量：转换结束后已占 D+Z=5，安装只再需4。具体项目的 Z、选中成员和文件系统空间均需实际测量。

## 6. 删除优先的精简原则（2026-10-16修订）

本节及第9、10节取代初稿中“保留短期授权并自动续期”“固定预算耗尽再续轮”“先构造通用事实依赖机制再放宽”等决定。用户要求直接删除没有实际必要性的防御策略，不接受为维护旧限制而增加新线程、快照、例外表、重试状态和配置项。

判断顺序：先指出检查实际防止的错误，再看已有文件校验、锁、取消或恢复机制是否已经覆盖。不能指出独立作用的门槛及其专属配套代码一并删除。确实有必要的检查只在需要的边界执行；同一不可变输入在同阶段复用结果，跨进程、文件重新打开或外部可变边界仍核实身份和摘要。

### 6.1 删除的人为限制

- 删除短期安装授权、安装计划 TTL、自动续期和前台心跳租约的整套失效机制，具体边界见D01–D02。计划的记录时间可作诊断，不能决定是否允许安装；签名目录本身的有效期属于发布信任协议，不与本地安装计划混为一谈。
- 删除正常查询的固定总时长、总请求数及官方子预算，不用续轮包装这些限制；删除“两轮无进展”“等待超过300秒”自动结束查询的门槛，见D03–D04。
- 删除正常解析/转换仅因累计CPU或墙钟达到阈值就终止的规则，不用按包大小推算并封顶的公式替代，见D05。
- 删除全事实快照相等、整份manifest摘要相等、无关设置revision变化等总否决条件；普通复制不要求非必需版本/语言/DLC证据，见D06–D07。
- 删除按候选数量、来源名称、响应MIME代替实际资源/格式能力的拒绝条件，见D08–D10。删除旧来源TTL无调用常量及误导性注释，不恢复已经取消的时间过期行为。
- 固定2GiB空闲、流式摘要512MiB、原文件总量16GiB等许可线直接删除；按实际剩余占用检查空间，流式读取使用固定缓冲和checked算术。
- 不应用的ZIP时间戳/所有权元数据，不维护字段默认值白名单。必要格式结构、名称解码、链接和特殊文件判断仍保留；库解析器本身不支持的结构必须如实报错，不能声称应用层删判断就已支持。

### 6.2 保留有实际作用的检查和能力边界

- 文件路径不得越界、不得通过链接写到其他位置；名称无损解码、重复目标/文件目录碰撞、声明长度、CRC/SHA、流结束及原文件变化检查保留。
- 全部原文件备份、成员临时文件、校验后rename、journal状态、失败回滚和外部修改冲突保护保留；锁及恢复材料引用保留，均不依赖时间续期。
- 单次HTTP连接/读取超时、站点限速、逐跳主机/TLS校验、取消与实际网络失败处理保留。长期任务与单个阻塞I/O的超时分开。
- sandbox的权限/挂载/网络/进程隔离、实际内存与字典/递归/令牌资源边界保留。解析器只执行已实现的必要动作；未知动作报unsupported，不静默跳过。
- ZIP64、SF真实字段宽度、编码和大文件读取属于实现能力，必须补齐checked转换和端到端读写；SF的u16计数不是可删除的策略常量。
- 报告/索引/协议仅保留有独立资源依据的字节预算，去掉重叠数量许可线。字节单位不等于限制合理，现有512 KiB输出、4 MiB缓存等策略值也须按D08说明依据。未来确有大清单需求再扩展分页或流式能力，本次不先建立通用资源配置平台。
- 来源启用/订阅、选中的下载项、目标实例、可信发布要求及安装器实际条件继续按当前操作核对。明确条件不满足须报具体原因；无关信息缺失和整个对象变化不构成失败。

### 6.3 简化后的安装主链路

## 8. 验收标准

| 宿主调度停顿超过旧15秒心跳窗口 | 控制管道仍连接且未取消时任务继续；不因漏renew取消 |

| EXE解析/转换越过旧CPU/墙钟阈值 | 可取消且合法处理不因累计时长被杀；隔离、内存和格式边界仍有效 |

## 9. 查询采用直接持续遍历

一次点击启动既有任务，按来源遍历去重后的待办，产生候选即可发布。某来源遍历完成或实际失败后结束该来源，其他来源继续。所有来源均结束时，任务进入终态并保留已有候选及各来源错误；有失败不能冒充全部查询成功，也不能因错误尚未消除而一直保持运行。只有仍有实际待办、正在执行的请求或等待重试时刻的请求才继续运行。用户取消单独报告。复用既有任务终态和结果诊断表达成功、部分失败或全部失败，不为此另建重试状态机。切页不触发取消，返回可继续观察当前任务。

删除RequestContext的总deadline/请求预算/官方子预算，以及仅为绕过它们增加的progressive模式、renew_slice、计数清零和循环快照摘要。保留真实分页游标、已访问集合和可恢复检查点，用于分页、取消或进程中断恢复；不另造“每29秒结束一轮”的生命周期。若来源间需要调度，按实际待办与就绪状态调度，不将29秒换成另一个隐藏截止线。

每来源仅保留工作所需的待办、已访问标识、结果和重试时刻。429/Retry-After按该来源等待，连接/读取超时或真正失败按来源处理；不无限自动重试永久故障，也不新增统一重试平台。不得因一个host的最大等待时间让所有来源停摆，不把退避等待算成“游标不动”。

复用现有start/observe/cancel及事件通道，移除双方宿主renew转发与核心租约依赖。相同活动查询可复用任务；新查询使用既有task/generation区分，旧任务不能回写新查询。仅对当前来源启用/订阅和当前查询条件进行必要核对，不叠加全局revision和新的全对象摘要门槛。

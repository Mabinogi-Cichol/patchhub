# Decky 覆盖安装与 SACRIFICE VILLAINS ZIP 失败修复方案

日期：2026-10-10（方案基线；2026-10-11 更新施工状态）。状态：**已完成**：F1–F3 代码、双平台全量回归、独立复核（收口修复）、正式部署、Deck 三款游戏实机安装/覆盖/写入取消回滚/游戏内生效（用户确认）与 Windows 共享事务回归（旧收据 superseded 实机确认）均通过。

所属功能：[跨平台安装器迁移设计](design.md)；实际记录：[progress.md](progress.md)。本文第1–6节记录2026-10-10调研证据、产品决策和目标方案；2026-10-11 开始实现后，代码与实际验证状态以末节更新及施工记录为准。失败复现仍只代表正式旧版，不是修复验收。

## 1. 结论与归因

| 问题 | 已确认原因 | 与迁移的关系 | 修复方向 |
| --- | --- | --- | --- |
| 你妈真漂亮（2743810）、催眠学习（1788100）被“尚未核验”阻断 | P5 切换工具把旧 committed 实例及 AppID 写入 `preexisting-installations.json`；扫描禁用候选，安装入口在下载前拒绝 | **P5 新增产品策略**，不是游戏内容检测失败。当前没有给用户提供解除或核验入口 | 移除旧安装名单准入门；用户点击安装即可覆盖配方目标，以本次开始前的实际文件为回滚基线 |
| SACRIFICE VILLAINS（3137110）ZIP 失败 | 正式版旧失败记录及本轮复现均为 `analysis_failed`，详情 `zip_expansion_limit`；ZIP 中 `update1.ypf` 为 6,073,754,660 bytes，超过 4 GiB 单文件上限 | **旧 Python 与 Rust 都有相同上限**，不能归因为 Rust 新引入的 ZIP64 解析错误 | ZIP 容量按实际磁盘资源判断；共享配方与事务、哈希、恢复、检测全链路同步支持大文件 |

优先级：覆盖阻断与 ZIP 容量为 P1；YPF 目标映射与容量修复一起交付，避免“事务成功但补丁不生效”。游戏名、AppID 和样本 SHA 只用于回归，不作为放行白名单。

## 2. 证据与复现边界

### 2.1 当前代码

- [切换保护读取](../../../crates/core/src/installer/preexisting.rs)：`Protection::is_blocked` 按 instance **或** AppID 判断；没有载荷哈希或游戏内容核验。
- [CLI](../../../crates/cli/src/runtime.rs)：`scan` 追加 `preexisting_installation_requires_review`，令 `download_available=false`；`install_patch` 在签名 ZIP、动态 ZIP、动态 EXE 路由分发前直接拒绝。
- [共享 UI](../../../packages/ui/src/index.ts)：`patchInstallable` 拒绝有 blocker 的候选；`installSummary` 优先显示“已有补丁，需检查”；报错文案要求用户检查，但无可执行的核验流程。
- [切换工具](../../../scripts/check-decky-cutover.py)：`publish_protection` 从旧 committed 记录提取实例及 AppID；`safe_to_replace` 当前也依赖保护发布。
- [ZIP 配方](../../../crates/core/src/installer/zip_recipe.rs)：`validate_entries` 限制单文件 4 GiB、总展开 16 GiB、8192 成员、压缩比 200；`wrapped_xp3_paths` 仅在游戏有签名正确的 `data.xp3` 时处理一层 XP3 包装。
- [事务安装器](../../../crates/core/src/install.rs)：再次实施同类大小/数量限制；`hash_at`、计划加载、stage、备份、写入、恢复也受 `MAX_FILE_BYTES` 约束。因此只改 `zip_recipe` 常量不会完成修复。
- 旧 [publisher.py](../../../apps/decky/backend/publisher.py) 的 `MAX_FILE=4*1024**3` 和 `_wrapped_xp3_paths` 证明这两项 ZIP 局限在迁移前已存在。该文件不在当前生产安装链路中，不能通过修改它修复正式版。

## 3. 产品决策：一键覆盖安装

### 3.1 正常用户流程

- 已有补丁、旧版本安装、外部安装、缺少新收据、文件被用户修改，以及选择的补丁内容更新，均不单独构成“禁止覆盖”理由。
- 安装按钮明确表达“安装补丁”或“覆盖安装补丁”；用户点击即对本次后端生成配方中的目标执行覆盖，无核验向导、逐游戏审核或二次确认。
- 原文件摘要只代表本次操作开始前的实际内容。它用于处理期间的变化检测与失败回滚，不要求等于原版文件或上一次安装内容。
- 覆盖只处理本次配方的目标，不删除上一版多出的文件，不重置游戏、DLC、Proton 或存档。不同内容可以覆盖同目标，但不宣称完成旧补丁的全量卸载/跨引擎升级。
- 用户无需删保护文件、删数据库、重装游戏或人工修改收据。

### 3.2 统一语义与后端改动

推荐为协议新增明确的 `overwrite` 操作（旧 `install/reinstall` 保留现有语义用于原请求与历史），客户端正常安装按钮调用它；共享核心、Decky、Windows、DTO、请求绑定同步升级。不能把前端传来的 `force=true` 当作内容许可，也不能把覆盖偷偷映射为旧 `install`。

具体实施：

1. 删除生产扫描和安装入口对 `preexisting::load` 的依赖。旧 marker 即使存在或损坏，也不阻断正常覆盖；不读旧 journal，不把旧 marker 当作安装成功证明。移除“需检查”状态优先级与死路文案。
2. 切换工具取消 `--write-protection`/保护存在性门槛，仍检查旧活动任务和未完成事务、保留恢复材料；历史文件可以留档，正式运行时不消费，不通过清空 state 解除。
3. 在 `ensure_no_active` 中允许 `overwrite` 遇到同实例已终态的 committed，继续拒绝 applying/rolling_back/needs_recovery/uninstall 中的事务；已有游戏锁、请求幂等与租约保留。
4. `prepare` 的 `overwrite` 分支以现场文件生成新 plan；不要求旧 release/content/build/文件集合相同，不运行同内容 `Reinstall` 的拥有性门槛；`apply` 再核对本次现场快照。签名目录继续核对包摘要/可信配方，覆盖意图不能修改签名内容。
5. 成功提交时新事务 committed，旧 committed 原子标记 superseded（复用现有提交算法）；失败/取消只恢复到**本次开始前**，原成功收据保持原状态；历史页面可追踪覆盖顺序。
6. ZIP、签名 ZIP、EXE 使用相同覆盖意图。EXE 已有 `reinstall_evidence`/`evaluate_with_reinstall` 不能仅删除 error：SF 行为分析、平台/语言/DLC 和真实脚本条件继续求值；旧收据或覆盖点击都不能伪造条件满足。旧拥有性仅用于旧同内容重装的特殊基线语义；覆盖按当前现场条件决定能否生成完整载荷。遇到真实脚本条件不满足时显示具体条件，不恢复“未知旧安装需人工核验”总闸。

缓存许可需要随策略/操作契约更新失效，已有未完成事务按原计划恢复；不要为了新增枚举让旧 journal 反序列化失败。请求绑定必须包含 operation，新覆盖请求使用新 request_id。

## 4. ZIP 资源策略：取消低固定业务上限

用户指出固定文件大小和数量上限会造成大量限制。本方案不采用“4 GiB 改成 8 GiB”作为最终产品策略，也不新增用户手动设置大小/条目数的流程。

### 4.1 用实际资源代替容量猜测

- 普通 ZIP 不再因为单文件 >4 GiB、下载包 >8 GiB、展开总量 >16 GiB 或成员 >8192 就失败。这些数值是现有实现策略，**不是 ZIP64、Rust 或 SteamOS 的必然限制**。
- 获取、载荷哈希、stage、备份、写入、回滚与检测均流式处理，固定大小 buffer；不把文件大小转换为整文件内存分配或 `u32`。
- 已知 Content-Length 时检查下载卷可用空间；未知时逐段检查实际写入/空间，错误清理本次 partial。ZIP 中声明的展开量用于预检，实际展开仍验证 CRC、字节数与载荷摘要；声明不能作为跳过真实检查的许可。
- 按各文件当前原件大小、stage、新文件临时副本和恢复副本估算峰值，按**实际卷**汇总；state 与游戏同卷时计入共同峰值，异卷分别计算，明确列出当前算法的保守余量。进入写入前再次检查可用空间；运行期间空间耗尽仍按事务回滚，不可能靠一次预检消除外部占用。
- 高压缩比不能独自证明异常，不用固定 200 倍拒绝合法压缩资源；按实际展开预算/长度、磁盘、取消和资源调度控制处理，保留压缩格式/CRC/截断与越界错误。
- FAT32 等目标文件系统自身存在真实单文件限制时，按目标能力/实际 I/O 错误说明原因；不把该限制强加给所有 ext4/NTFS 用户。

### 4.2 保留有依据的运行资源边界

取消上述业务常量，不等于无限分配内存、无限解析恶意目录或忽略路径安全。ZIP 路径穿越、符号链接、特殊文件、大小写冲突、重复目标、非法路径和恢复材料保护继续执行。

成员数量影响中央目录、映射、JSON 授权/计划、SQLite job 持久化及路径冲突算法，不只是数据大小。实施前做 10k/50k 小文件压测，测内存、计划体积、耗时与取消响应；依据这些结果给中央目录/元数据设置宽裕的**字节/内存预算**和清楚的资源错误。必须检查当前 `ZipArchive::new` 可能在条目校验前分配目录内存。优化逐目标 O(n²) 冲突检查和超大 job 反复整份写入，避免仅删 8192 限制后卡死；若仍需总成员兜底，必须给出实测理由和高于正常补丁需求的边界，不能照抄旧值。

授权 JSON 当前 4 MiB、宿主单行响应 8 MiB 等属于元数据/协议限制；大量文件若撞到这些边界，应优化内部存储及对 UI 的摘要投影，并提供具体资源错误，不悄悄形成第二个低条目门槛。

本次资源策略针对 ZIP 数据安装链路。SF EXE 隔离 worker 的 AST 深度、对象图、解析内存/时间和 2 GiB 格式支持仍属独立能力边界；本轮不据此宣称 EXE 任意尺寸可用。

### 4.3 必须贯通的代码面

| 代码面 | 必须修改/核对 |
| --- | --- |
| `installer/acquire.rs` | ZIP 下载、缓存重哈希、总量 hint 与资源判断；EXE limit 分离 |
| `installer/zip_recipe.rs` | 成员/实际展开统计、目标现状哈希、映射后容量与元数据预算 |
| `installer/orchestrator.rs` | apply 前按实际长度 `facts::digest_file(path, fs::metadata().len())` 重核、新映射与授权绑定 |
| `install.rs` | `prepare`、计划读取校验、`hash_at`、stage、`copy_checked`、临时文件恢复、已有目标/备份哈希；全部 `MAX_FILE/MAX_EXPANDED/MAX_ARCHIVE/MAX_ENTRIES` 使用点 |
| `catalog.rs` / CLI 检测 | `MAX_FINGERPRINT_BYTES=4 GiB` 会导致大文件安装后无法正常检测；同步改成流式与实际资源语义 |
| 计划/授权/请求版本 | ZIP 策略与映射变化使未执行授权失效；不误改旧事务恢复或 EXE 内部语义 |

本样本完整展开约 6.41 GiB，磁盘有约 50 GB 可用；当前拒绝不能归因为空间不足。修复后仍须按实际峰值重新核对。

## 5. YPF/pac 包装层映射

### 5.1 规则

在既有 XP3 专用规则旁增加结构明确的 YPF/pac 规则：

1. 非目录成员全部位于唯一共同外层目录；其下存在 `pac/` 资源层，无多外层或混合游戏根文件的歧义。
2. 游戏根已经有普通 `pac/` 目录，至少一个正常 `YPF\0` 资源；包中至少一个对应的正常 YPF 资源/新增 update 资源支持该引擎布局。游戏目录与候选成员均无链接，目标仍在游戏根。
3. 对该布局去掉恰好一层外包装；**保留 `pac/`**。例如 `sacrifice_villains_fullpatch/pac/update1.ypf` → `pac/update1.ypf`。
4. 本样本全部载荷都是 `.ypf`，允许真实 YPF 和本轮实测的 ASF 视频首部；不按扩展名要求全部是 YPF，也不解析或执行载荷。映射规则不对所有 ZIP 执行无条件 strip-first-component。
5. 映射后重新核对重复/大小写/文件目录冲突与原文件快照。包布局不符合规则时给出具体布局原因，不生成看似成功的错误目录。包无说明文件，本期不推断说明应删除；其他结构需单独明确映射证据。

映射输入、策略版本及目标摘要纳入当前配方/内容授权；以当前 ZIP 的实际字节重建配方，不复用旧错误目标。无逐游戏配置表、不靠样本 SHA 放行。

### 5.2 不应采用的修补

- 只提高一个 4 GiB 常量：下游 stage/哈希/恢复/检测仍失败。
- 只删除 marker 文件：新部署可再次写回，旧重装拥有性门槛仍在；用户继续被要求自行处理。
- 只把所有“重新安装”改为 `install`：当前已 committed 会命中 `managed_install_exists_or_needs_recovery`。
- 只对当前 AppID 或 URL 特判：下一款同结构游戏还会失败。
- 把整个 ZIP 解到游戏根再宣称成功：本样本会留下外层 `sacrifice_villains_fullpatch/`，游戏 `pac/` 没有收到载荷。
- 把 `analysis_failed` 统一解释为 ZIP 损坏：本例真实详情是资源策略拒绝。

## 6. 错误与进度

- 资源不足提示实际需求、可用空间和对应卷；不让用户猜“分析失败”含义。
- 缓存重哈希增加“检查已下载补丁”子阶段。当前通过受信 facts 哈希器重核，因其尚无安全的字节回调，仅显示验证阶段，不伪造字节进度。
- 将文件尺寸、元数据资源、ZIP 布局、CRC/截断错误分开呈现；技术详情可以留操作记录，主提示说明可采取的动作。
- 取消、失败终态继续绑定原实例，旧历史不自动弹出。上述验证阶段文案已在代码接入，实机页面待验。

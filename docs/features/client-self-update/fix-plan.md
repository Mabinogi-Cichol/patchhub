# Windows 自更新进度与多实例失败修复

- 设计：[design.md](design.md)；施工记录：[progress.md](progress.md)。
- 分支：`fix/windows-self-update`，基于 `main@2bf0dda`。

## 证据与原因

- 用户截图中下载界面只显示字节数；`AppUpdatePanel` 的 downloading 分支没有进度条。
- 本机 `last-update-result.json` 记录的安装错误为 `Application still running in target directory`，目标为仓库内 Flutter Release 目录。它不包含 `HandshakeException`；后者是另一次网络操作的异常，旧界面将两个结果相邻展示，容易误读为同一错误。
- 只读检查发现目标目录有两个由 Explorer 启动、仍有响应窗口的 PatchHub 实例（PID 1216100、1253460）。助手只等待发起更新的 ParentId 退出，之后才检查整个目标目录；另一实例会导致发起者已关闭但替换未开始，因而不会启动新版。

## 最小修复

1. 下载弹窗显示进度条、百分比及可读大小；未知总长度时显示不定进度。下载开始及切换附件时重置计数，显示核对发行信息、下载校验清单、下载 ZIP、校验 ZIP 阶段。
2. 助手在写 prepared 标记、允许当前客户端退出之前检查同目录其他 GUI 实例，报出占用进程和 PID；准备阶段允许调用者及其尚未关闭的 Core 工作。保留退出后的全部进程检查，避免在占用状态下替换文件。不强杀其他窗口，不增加固定延时或自动重试。
3. 分开展示上次安装结果与本次操作错误；解释目录占用与 TLS 握手错误，并提供重新检查入口。保留原始异常，继续使用现有 TLS 证书验证。
4. 2026-10-28 追加单实例：在 Windows 原生入口、Flutter/后台任务启动前取得会话级 PatchHub 命名互斥量，整个进程生命周期持有。重复进程唤起已有窗口后退出；最小化时还原。安装版与便携版共用用户数据，因此同会话也互斥。新版 `--update-probe` 同样遵守单实例规则，旧进程实际退出后由助手启动即可取得互斥量；不豁免更新启动，不增加进程轮询或等待阈值。已实现，原生模块回归与真实 Flutter 夹具链验证通过，详见施工记录。

## 验证与边界

- Widget：已知/未知长度、进度变化、历史安装错误与本次握手错误分离、重新检查。
- 服务：新下载清除上一次进度。
- 真实 Windows 助手：另一个同目录实例在准备阶段阻止退出；调用者自身允许准备并在退出后更新；另一目录实例不阻止更新；沿用并重跑已有替换/恢复/卸载测试。
- Windows 单实例：原生真实进程验证重复/并发启动、最小化还原、正常退出/异常退出后重新启动及更新探针启动。使用独立互斥量标识的测试夹具，不影响用户当前窗口。
- 自动化结果写入施工记录；未执行的真实 GitHub 跨版本更新、系统安装版及用户现有窗口操作不记为通过。

# Windows 设置入口与缓存管理设计

状态：已实现，定向自动化与真实字体渲染验证通过；原生窗口及用户验收待完成。施工记录：[progress.md](progress.md)。交互示意：[ux-prototype.html](ux-prototype.html)。

缓存页布局示意：[ux-cache.png](ux-cache.png)（独立绘制的设计图，非实际应用截图）；三个页签及模拟交互以 HTML 示意为准。

## 目标与范围

将 Windows 客户端的一级“全局来源”入口改为齿轮图标的“设置”，设置内包含“全局来源 / 缓存管理 / 关于”三个二级页签。取消正常状态下常驻的版本与检查更新栏；自动发现新版本时仍在全局底栏持续提示。本轮实施 Windows 设置与缓存管理，使用隔离状态目录验证清理；不部署、不清理真实缓存。

仅覆盖 Windows Flutter；Decky 不同步改版。沿用现有深浅主题、字体、控件及来源管理能力。

## 页面与交互

### 一级入口与设置框架

- 游戏界面标题栏右侧显示齿轮图标＋“设置”；保留外观入口与窗口按钮。图标提供“设置”语义标签与提示。
- 点击后进入设置，标题栏入口切换为“返回游戏”。左侧原游戏列表区域替换为设置导航，右侧显示当前页签；不叠加第二条侧栏。
- 设置左侧宽度 232px，包含“设置”分组标题、全局来源、缓存管理、关于；选中项使用现有蓝色强调与底色，并有文字与图标提示。
- 首次进入默认“全局来源”，本次运行再次进入时保留最近页签，不增加磁盘持久化配置。返回游戏保留选中游戏、筛选条件、搜索和原列表位置。
- 返回游戏不取消来源更新、重匹配、缓存清理或应用更新任务。页面切换复用原任务状态，不重新启动任务。
- 内容区独立滚动；标题栏、设置导航和有更新时的底栏固定在布局中，避免遮挡末尾内容。最低窗口沿用现有 850×560，内容区按宽度换行，不增加新分辨率门槛。

### 全局来源

迁入原有 GlobalSourcesPage：保留脚本来源导入、全库重新匹配、发行商来源、补查来源、来源展开操作及任务状态。保留“单个游戏的订阅请进入游戏订阅”说明。只调整容器与间距，不重写业务逻辑。

### 缓存管理

首版提供一组“下载与临时缓存”，一个占用数字、“刷新占用”和“清理缓存”按钮。使用“缓存占用”而不是“预计可释放”，因为当前统计不扣除受保护文件，且任务元数据回收不纳入同一个统计口径。示意中的大小、文件数、版本与时间都是演示数据。

范围以现有核心 CacheService 为准：content、downloads、reports 三个允许清理的目录，以及核心判定可回收的任务元数据。正文可概括为下载包、处理缓存和临时报告。界面同时说明：再次安装可能需要重新下载；保留来源索引、订阅配置、游戏文件、已安装补丁和安装恢复材料。不把来源数据重置、图片缓存清理或备份删除纳入本轮。

交互流程：

1. 进入页签调用 cache_status，展示加载状态；成功显示 total_bytes 与 entries，diagnostics 非空时说明“部分文件无法统计”，不要显示为完整统计或 0。
2. 点击“清理缓存”弹出一次确认，明确范围及重新下载影响；不重复确认，不要求输入文字。
3. 确认后调用 cleanup_cache；当前按钮显示“正在清理…”并禁用重复点击，允许切换页签；不制作虚假百分比，不设置任意超时，不添加自动重试。
4. completed：显示实际 removed_bytes，重新统计；partial：显示已释放大小与未清理项，提供错误详情与手动重试；failed：显示失败原因；installer_busy 或 busy：提示“有安装任务正在使用缓存，请任务结束后重试”，不强行取消安装、不排队重试。
5. 清理完成但重新统计失败时分别保留清理结果和统计错误。空缓存显示 0 B 与“暂无需要清理的缓存”；统计失败显示“占用读取失败”及重试，不伪装成空缓存。

清理不应仅由页签 widget 持有任务生命周期；使用现有模型/核心调用管理，避免离开页面丢失结果。不引入通用清理框架或新的缓存策略设置。

### 关于

显示 PatchHub、简短用途、当前实际运行版本、更新状态、“检查更新”按钮及最近成功检查时间（尚无记录则明确显示）。当前版本沿用 app-version.json 的读取结果，不硬编码截图中的版本。

- 手动检查：按钮显示“正在检查…”，完成后在本页显示最新/可更新/失败状态；无更新不产生底栏，失败展示实际错误和重试入口。
- 有更新时显示版本、“查看更新”；复用原有更新详情、下载、取消、下载进度与重启更新链路，不再创建另一套下载或安装状态。
- 后台自动检查仍在应用级初始化，不能改成打开“关于”后才开始；保持现有调度规则，本轮不调整检查频率。

### 全局更新底栏

- 没有新版本：不渲染底栏，不预留空白高度；当前版本和检查按钮仅放在“关于”。
- 自动发现新版本：游戏页与设置所有页签底部都显示“发现新版本 v… / 查看更新”。手动发现新版本时也显示同一底栏，避免退出关于后丢失更新入口。
- 底栏不提供“稍后”关闭，满足“常驻”要求；原有详情弹窗的“跳过此版本”仍保留，显式跳过后该版本不再提醒，更高版本重新提示。
- 打开或关闭更新详情不清除底栏。开始下载后底栏继续显示真实阶段/进度及“查看进度”，下载完成显示“更新已就绪 / 重启更新”；失败显示简短状态与“查看详情”。具体按钮复用原更新组件，避免重复业务入口。
- 安装更新成功并运行新版本后旧提示消失；更新详情的取消、跳过行为与状态须定向回归，不能继续用 lastCheckWasManual 或页面局部 dismissed 阻断常驻提示。

## 实施拆分与验收

1. 设置壳与来源迁入：齿轮入口、三个页签、返回游戏状态保持；全局来源原操作回归。
2. 关于与底栏：迁入版本/检查入口、复用更新详情与更新状态；正常无底栏，有更新跨页保持，覆盖手动检查、下载、取消、失败、就绪、跳过。
3. 缓存管理：统计、确认、清理、结果与错误接线；覆盖空缓存、统计失败、部分统计、完成、部分失败、占用和重复点击。
4. 定向验证和实机视觉验收：受影响 Flutter 测试、flutter analyze、格式检查；实际深浅主题、1180×760 与 850×560、文本缩放、键盘焦点和内容滚动检查。隔离状态目录验证清理结果及受保护数据，不删除用户真实缓存。不运行发布前完整 CI matrix，不发布、不部署 Deck。

## 方案审阅

按 overengineering-review 对入口→设置→现有业务和统计→确认→清理→结果路径做方案审阅：采用直接页签状态、现有核心接口和同一更新模型，未发现需要新增通用路由框架、分类清理协议、持久化导航设置、TTL 或自动重试的依据。保留的确认来自删除下载包的实际影响；核心互斥与目录边界用于避免清理在用安装文件和恢复材料。统计口径不是可释放估算，已避免误导性承诺。此结论是方案静态审阅，不代表实现或实机验收通过。


## 实施补充

- 缓存状态由 AppModel 持有 CacheModel，首次打开缓存页才统计；页签与游戏界面切换保留任务、结果和各自滚动状态。
- 关于页通过 AppUpdateScope 使用同一 AppUpdate 和详情动作；不新增下载/安装链。取消下载或准备重启失败后保留错误与详情入口。
- 为满足新版本常驻与已下载就绪入口，复查期间及失败时保留已发现版本，ready 状态不发起复查；原有日/小时调度和服务限流规则保持原样。
- 使用现有主题强调色绘制设置选中项；固定 232px 侧栏避免最低窗口 1.5 倍文字时四字导航换行。内容独立滚动，底栏占用布局空间。

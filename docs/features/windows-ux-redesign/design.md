# Windows 交互重设计

状态：整体交互方案已获用户认可；按用户要求改为 Flutter 重写，技术实施于 2026-10-22 开始，P0/P1 进行中，整端待实现与验收。施工记录见 [progress.md](progress.md)。

## 1. 目标与依据

以 Decky 的任务分层为参照，改善 Windows 找游戏、选补丁、安装、查看结果与管理来源的完整路径。保留桌面端快速切换游戏的优势，不照搬手柄导航。

静态检查基线：main `4079692`。依据：[Windows 页面](../../../apps/windows/src/main.tsx)、[样式](../../../apps/windows/src/style.css)、[来源面板](../../../apps/windows/src/SourcePanel.tsx)、[宿主](../../../apps/windows/src-tauri/src/main.rs)、[Decky 页面](../../../apps/decky/src/index.tsx)、[Decky 设计](../decky-ux/design.md)、[来源折叠设计](../source-cache-matching-refactor/collapsible-source-cards/design.md)。当前判断来自源码，不是 Windows 实机体验验收。

当前具体问题：
- 游戏详情把检测、兼容性、技术标识、安装、来源匹配、事务全部纵向排列，主要操作被信息淹没。
- 顶部长期出现全局恢复按钮；全局来源抽屉又混入所选游戏订阅，作用范围不清楚。
- 安装进度在页面上方挤占布局，结果只保存在全局 notice/error；缺少明确的结果停留页。
- 多补丁用可换行按钮堆叠；来源线索与可安装条目混在同一层选择。
- 来源卡片默认铺开全部调度元数据，阅读成本高。

## 2. 信息架构与布局

保留现有默认窗口 1180×760、最小 850×560，实施时验证 Windows 125%/150% 缩放。

```text
Steam 黄油补丁助手                          全局来源
────────────────────────────────────────────────────
游戏库（约 260px）  │ 当前游戏完整名称 / 当前状态
搜索名称或 AppID   │ 概览  补丁管理  操作记录  游戏订阅
筛选：有补丁 ▾       │ ──────────────────────────────
                   │ 当前栏目内容
游戏 A   有补丁    │
游戏 B   已安装    │
游戏 C   需处理    │
                   │
重新扫描游戏库     │ 补丁管理内：条件摘要 + 主操作
```

- 左侧承担选游戏，右侧承担当前游戏操作；不再增加一列侧边栏。全局来源作为独立内容页，提供“返回游戏”，恢复原选择、筛选与滚动。
- 游戏切换默认进入概览；同一游戏分栏切换保留已选补丁和阅读位置，切换补丁清除旧文件选择、预览及手动确认。
- 列表展示名称和一行状态；多安装实例附库位置用于区分。详情完整显示长名称；路径允许换行，不依赖悬停才能读到关键条件。
- 默认筛选为“有补丁”，与 Decky 的 `matched` 口径一致；用户手动切换后，本次会话内保留选择，刷新和返回页面不重置。无结果时提供“查看全部游戏”，不自动改成全部。
- 搜索筛选只作用于已有结果。刷新保留旧列表，显示局部扫描状态；区分未扫描、无游戏、无筛选结果和扫描失败。
- 支持 Material 3 浅色与深色主题，默认跟随系统；顶部“外观”菜单可选择跟随系统、浅色、深色，本次会话保留选择。切换主题保留当前游戏、筛选与页面状态，不触发扫描。
- 桌面采用鼠标/键盘原生操作：可见焦点，Tab/Shift+Tab 可达，Enter/Space 激活；不复制 Decky 跑马灯和手柄按键提示。

## 3. 游戏概览

首屏回答“目前什么状态、找到哪些补丁、下一步是什么”。

- 顶部显示游戏名和一个主状态，匹配状态与安装状态用不同文案，不把“有来源”写成“已安装”。
- 可安装补丁列表展示名称、具体来源、语言、格式、适用条件摘要；每项主操作“查看并安装”，进入已选补丁的管理页。
- 来源线索独立成“待核对的来源”，操作为“查看条件与来源”，不伪装成可安装项。
- 仅一个可安装补丁也进入管理页确认条件，不在概览增加另一套安装入口。
- 游戏编号、build、路径放“游戏信息”折叠区；匹配错误/来源不完整则直接显示，不能被折叠隐藏。
- 无匹配时显示“已启用来源中未找到补丁”，提供重新匹配与游戏订阅入口，不断言游戏无需补丁。

## 4. 补丁管理

```text
补丁：[补丁名称 ▾]                  多个补丁时才显示选择器
来源名称 · 简体中文 · EXE          来源网页 ↗
适用条件：本体 / DLC 条件；未知时如实标明
当前状态：未安装

[下载项/镜像 ▾]                    仅有多个选择时显示
必要的兼容提示或手动选择确认

▸ 文件与技术详情
▸ 使用本地 ZIP                    仅核心允许此路线时出现

安装时请关闭游戏并暂停 Steam 更新    [安装补丁]
```

- 主按钮沿用核心 action contract：安装、覆盖安装、需要选择本地 ZIP、不可安装。按钮旁显示不可用原因，不让用户猜测。
- 来源名称使用具体订阅源名；未知来源如实显示，不无依据写“官方”。补丁语言、DLC 条件、兼容性阻断始终可见。
- `manual_selection_required` 保留明确确认；选择补丁或镜像后撤销旧确认。没有此要求时不增加泛化确认弹窗。
- 自动安装为主路线时，本地 ZIP 折叠为次要入口；主路线要求本地 ZIP 时，直接呈现文件选择，不能藏起来。
- 文件变更预览是可选只读工具，不作为安装的必经步骤；release/selection ID、完整 URL、匹配依据放可展开详情。
- 首屏和底部操作区只有一个主要安装按钮；窄窗内容换行且不遮挡底部内容。

## 5. 安装、取消与结果

点击安装 → 立即打开前台进度对话框 → 接收真实进度 → 切换独立结果内容 → 关闭后回到原补丁。

- 进度显示游戏、补丁、当前阶段、可获得的已处理/总量与文件信息。数量可读化为 MB/GB，未知总量不造百分比；速度仅在有可靠数据时显示。
- 对话框不允许遮罩点击静默消失；运行中唯一退出操作为“取消安装”。Esc 等价于取消，等待真实终态期间显示“正在取消并处理已修改文件”，不提前宣称已恢复。焦点保持在对话框，结束关闭后返回触发按钮。
- 不提供后台安装、任务队列或额外重试机制。来源更新仍是原有独立任务，局部展示状态，切换栏目不取消。
- 最小化不等于取消。关闭整个应用沿用宿主现有 CloseRequested 取消并等待任务退出行为；需在实施时验证取消期间的界面反馈，不能承诺现有宿主一定会保留结果窗口。
- 结果区替换进度条，明确区分成功、失败、已取消、仍需恢复；取消与提交竞争以核心结果为准。关闭结果不会重新发起取消。
- 失败显示具体原因；仍需恢复显示相关操作和记录入口。刷新列表失败不覆盖安装真实结果，单独提示“安装已完成，状态刷新失败”。
- 可关闭结果面板；结果也在操作记录中可查，界面刷新不应把失败描述成成功。重试由用户返回补丁页主动操作。

## 6. 操作记录与恢复

- 当前游戏记录用补丁名、实际状态和已有时间字段呈现；技术 ID 收进详情，字段缺失不伪造。
- 需要恢复时在概览与记录页提示；恢复入口移到异常记录附近，正常状态不在顶部长期占位。
- 注意现有 `recover` 为全局调用，不能把按钮暗示为“只恢复此游戏”。执行前列出会影响的未完成操作并注明“恢复全部未完成操作”，确认后复用原调用。
- 既有能力不支持的卸载/恢复原版入口不增加；外部安装不能声称可由工具卸载。

## 7. 来源管理

- 全局页管理来源启停、更新间隔、更新索引与添加规则；游戏订阅页只管理哪些来源用于该游戏及语言偏好/重新匹配。
- 全局来源采用 Decky 可折叠卡片：默认收起，标题保留来源名、启用状态、更新时间摘要及正在运行/失败摘要。展开可操作，多卡可同时展开。
- 展开选择仅在本次会话保留，折叠不终止任务、不触发 RPC。
- 发行商源与 HGamer 补查源分组，补查源明确说明按游戏补查、不参与定时索引更新。
- 来源更新与游戏重新匹配保持既有不同语义，不用一个含糊“刷新”按钮替代；错误就近显示并提供实际对应的操作。
- 添加规则保留高级入口；内部 settings revision、原始诊断和详细地址放详情。

## 8. Flutter 重写边界与实施拆分

2026-10-21 用户指定 Windows 改用 Flutter 重写。本轮继续完成方案修订，不将技术选型确认记作已经完成开发。已认可的布局、交互和默认“有补丁”筛选保持不变。

### 技术选型

- Windows 客户端改为 Flutter + Dart，使用 Flutter 自带的 Material 3 控件与统一主题；列表、表单、菜单、对话框、反馈和焦点行为优先使用现成控件，不重新实现基础组件。
- Flutter 替代 Windows React/Vite 前端与 Tauri 桌面宿主；Decky 保持现有实现。
- 保留 Rust 核心、安装器、来源匹配、事务与现有进程 JSON 通信协议。首选 Flutter/Dart 调用既有核心可执行文件，不另建 HTTP 服务，也不同时引入一套 FFI 接口。
- 不能直接复用 TypeScript 的 @steam-patch/ui 或 Tauri invoke。Dart 按现有协议映射数据；展示层需要迁移筛选、条目合并、状态文案及主操作判断，核心返回的安装能力仍是依据，避免把业务判断搬入 UI。

### 宿主迁移是必需范围

现有 Tauri main.rs 同时承担核心进程定位/启动、协议校验、请求响应与进度转发、安装取消、来源任务及调度、文件选择、外部链接和应用退出处理。上述行为需逐项建立迁移对应关系，不能把只读扫描接通当作整端重写完成。

- 先用 Flutter/Dart 到现有 Rust CLI 验证能力查询、扫描、来源读取、任务事件与取消通道；核对 Windows 隐藏子进程窗口和打包后资源定位。
- 安装期间关闭应用必须沿用受控取消并等待实际终态的语义；最小化不取消。不得用强杀进程替代安全取消，不增加任意超时。
- 来源更新、自动调度与单游戏匹配沿用既有行为；切换页面和折叠卡片不影响宿主任务。
- 数据目录、来源设置、事务记录、下载与恢复材料的路径必须核对并保持连续；新客户端首次启动不得生成一套隔离数据而表现为旧记录丢失。
- 文件选择、打开来源网页、窗口关闭拦截等桌面集成在实施时选必要插件；在实际 Flutter SDK 与插件兼容性验证前不固定未经核验的版本。
- 协议映射以仓库协议定义与样例为依据；先使用直接类型映射，只有实际维护需求才引入生成工具。

### 分阶段实施

具体工作包、模块落点、依赖与退出条件见 [implementation-plan.md](implementation-plan.md)。该计划替代此前六条概要迁移顺序；实际执行结果只记录到 [progress.md](progress.md)。

依赖顺序为 P0 基线与工程 → P1 核心通信与旧数据；P2 任务宿主、P3 游戏浏览具备后，可分别推进 P4 来源管理和 P5 安装/结果/恢复，P5 不等待整个 P4。两者完成后联调来源到安装，再完成 P6 包验收和 P7 实机验收与旧版退场。P3 可先用固定数据做布局，但接入真实安装前必须完成 P2。Flutter 最终目录固定为 apps/windows-flutter，从 P0 使用到最终交付，不在验收后搬迁；打包验证从早期开始。迁移对应信息集中维护在实施计划第二节，不另建重复映射文档。

本轮不增加缓存/备份清理等原 Windows 未暴露的功能。不引入通用任务中心、新后端协议、任意超时或大小限制。状态管理先按页面与任务生命周期组织，不预先堆叠额外框架。

## 9. 验收标准（逐项实际证据见施工记录）

- 浅色、深色及跟随系统均可用，主题变化不重置游戏上下文；两种主题的文本、状态、焦点与禁用态均可辨识。
- 搜索→选择游戏→查看补丁→安装→看到结果→返回，始终知道当前游戏与操作状态；正常路径不需要打开高级信息。
- 多补丁、多镜像、本地 ZIP 主路线、手动确认、不可安装、仅来源线索均不丢入口或误启用安装。
- 安装成功/失败/取消/仍需恢复、安装结束后刷新失败分别呈现正确结果；结果不会因全局通知更新而丢失。
- 全局恢复准确展示影响范围，不伪装成单游戏操作。
- 来源任务切页不中断、折叠时进度/失败可见、展开不调用业务接口。
- 1180×760 与 850×560，125%/150% 缩放，长中文名/路径/错误、空列表、键盘焦点和对话框返回均可用。
- 未执行真实安装/取消恢复前，不把演示原型或合成事件视作实机通过。

## 10. 过度设计审阅

2026-10-21 对本方案静态自审：未发现需另加机制的项目。页面拆分对应现有信息混杂；结果面板对应安装反馈丢失；全局恢复范围呈现对应现有 recover 实际作用域。沿选择→安装→取消/结果→回到补丁及来源折叠路径检查，不增加后端流程或无依据防御。结论只针对计划，不是独立代码审查或实机验收。

## 11. Flutter 修订的过度设计复核

2026-10-21：Flutter 为用户明确技术要求；宿主迁移对应现有 Tauri 的真实职责，属于必要范围。采用既有 CLI 协议可复用核心业务；不同时引入 HTTP/FFI 两套通路。Material 3 基础控件优先，避免重新实现对话框和键盘焦点。此为计划静态自审；桥接可行性、插件组合、关闭取消及打包迁移均待实际验证，原 §10 结论不代表 Flutter 实现已通过审查。

# Flutter 重写实施计划

关联：[交互与技术设计](design.md) · [施工记录](progress.md)

状态：2026-10-22 P0–P7 已完成实施和本地/用户实机验收，旧端已退役。用户明确接受官方 ZIP Cloudflare 403 为外部遗留并授权完成及合回 main；证据与交付边界见施工记录，未推送、发布或部署设备。

## 一、施工组织与最终交付

在 `feature/windows-ux-redesign` 完成。Flutter 工程最终目录固定为 `apps/windows-flutter/`，从 P0 起构建、CI 和打包均使用此路径，验收后不再搬迁。旧 `apps/windows/` 在迁移期间用于对照，P7 删除其专属代码与入口；历史对照和发行回退使用 Git 基线及既有产物，不长期维护两套 Windows 客户端。下文 Flutter 文件均为拟新增，旧代码路径为已核对入口。

最终交付不是一个能运行的 Flutter 界面，而是：

1. 已确认交互的完整 Windows 客户端，默认筛选“有补丁”。
2. 可替代 Tauri 的宿主能力：真实扫描、来源任务、调度、安装、取消、恢复和安全退出。
3. 旧数据继续可读的便携包与安装包、可复现构建、CI 与必要使用说明。
4. 对应自动化、真实窗口、真实核心任务与升级验证证据。

每阶段施工记录必须列修改文件、执行命令、结果和未验证项。失败留在所属阶段解决；不以“页面已画好”替代接入通过。文档与代码分别提交，不为阶段编号机械拆分独立功能。是否提交/发布按届时用户指令执行。

## 二、模块落点和迁移对应

Flutter 起步用直接的数据模型、服务与页面状态，使用 SDK 提供的状态通知能力。下面是职责划分，不要求每个概念提前搭一层抽象。

| 现有入口/职责 | Flutter 拟落点 | 迁移原则 |
| --- | --- | --- |
| Tauri `binary/config_file/common_params` | `lib/host/core_paths.dart` | 确认核心、worker、资源与旧 state_dir；不使用 Flutter 新应用名默认生成另一个状态目录 |
| `require_capabilities/run_one_shot/validate_response` | `lib/host/core_client.dart`、`protocol_models.dart` | 使用 v5 JSONL 与现有能力契约；错误完整传播 |
| `read_core_stream/launch_source_task/start_install` | `lib/host/core_task.dart` | 每个任务独立子进程；消费事件与唯一终态，管理 stdin 控制 |
| `SourceTaskRegistry/select_due_sources/source_scheduler_tick` | `lib/host/source_tasks.dart` | 管理运行任务、既有去重规则与到期更新，不放进 Widget 生命周期 |
| `CloseRequested/exit_if_closing` | `lib/host/app_lifecycle.dart` | 关闭前受控取消并等待清理结束；最小化不取消 |
| 文件选择、外部链接、窗口信息 | `lib/host/desktop_services.dart` 与必要 Windows runner 配置 | 选必要桌面插件；不自己造文件选择器 |
| `packages/ui/src/index.ts`、Windows `sources.ts` | `lib/models/`、`lib/presentation/` | 迁移展示与选择语义；安装动作可用性继续取核心 DTO |
| Windows `main.tsx` 页面与状态 | `lib/app.dart`、`lib/pages/` | 页面壳、游戏列表与四栏目；选择状态与任务状态分开 |
| `SourcePanel.tsx` | `lib/pages/global_sources_page.dart`、`game_sources_page.dart` | 分离全局作用域与单游戏作用域 |
| `prepare-sidecar.mjs` 与 Tauri bundle | 拟新增 `scripts/build-windows-flutter.ps1`、安装包脚本 | 复制核心/worker/资源与 Flutter 运行依赖，继续交付两类包 |
| `.github/workflows/ci.yml`、根 package scripts、`scripts/run-windows-check.ps1` | 修改对应入口 | 增加 Flutter 检查与构建，清除退场后的 Windows npm/Tauri 引用 |

协议权威来源为 [crates/protocol](../../../crates/protocol/src/lib.rs) 与 [契约说明](../../../packages/contracts/README.md)，校验样例为 [v5 fixtures](../../../packages/contracts/fixtures/v5/cases.json)。不把 Tauri 命令名当作 CLI 方法原样发送，例如 `start_install` 对应 CLI `install_patch`。

## 三、P0：冻结迁移基线，建立可构建的 Flutter 工程

**目的：** 明确要替换什么，并尽早证明本机和 CI 能生成 Windows 应用。

工作步骤：
1. 读取当前分支、包版本、Windows 构建脚本和协议版本；直接补充第二节对应表中的保留能力、明确不做能力及待核实事项；不另建重复的迁移映射文档。
2. 核对 Flutter SDK 实际安装位置、Windows C++ 工具链与 Windows SDK。执行环境诊断；缺项按实际结果补齐，选定并记录 Flutter SDK 版本，CI 使用同一版本。
3. 建立 `apps/windows-flutter`，只启用本次需要的 Windows 平台；设定中文产品名、图标、1180×760 默认尺寸及850×560最小尺寸，使用 Material 3 主题。
4. 建立最小入口、页面壳和基础检查命令；验证文件选择、HTTPS 外部打开、窗口关闭拦截所需插件能在 Windows 构建。插件版本在验证后锁定。
5. 生成并启动一次 release 构建，从任意工作目录启动，确认不是只有 IDE/debug 可用。

**产出：** 补齐的第二节迁移对应表、Flutter 工程与锁文件、开发命令说明、首个可启动构建。

**退出条件：** SDK/工具链版本可复现；analyze 与最小测试通过；release 窗口真实启动；不影响旧 Windows 与 Decky 的现有构建。当前状态为待实施，不把先前 PATH 检查当成完成 P0。

## 四、P1：打通核心通信，并接续旧数据

**依赖：** P0。

工作步骤：
1. 实际解析旧 Tauri `app_data_dir` 和资源路径，记录当前机器上的确定值及推导规则；不能仅凭配置 identifier 猜路径。先复制用于验证的状态资料，不移动或删除旧数据。
2. 实现 `CorePaths`：开发与打包两种明确路径；使用现有 `steam-patch.exe`、`sf-worker.exe`、签名目录和信任钥。把 `host` 六字段原样按契约传递，保证新旧请求采用同一状态位置语义。
3. 实现一次性 `serve` 调用：按行写 JSON、关闭输入、并行消费 stdout/stderr、等待子进程退出。避免缓冲区占满导致阻塞，Windows 不闪控制台窗口。
4. 映射响应信封、DomainError、Capabilities、ScanResult、来源列表与事务记录。按 v5 规则核对版本和 request_id；不能将解析失败变成空游戏库，未知合法错误码保留 detail。
5. 顺序接入 `get_capabilities → scan → list_transactions` 和来源读取。核对旧版扫描与事务读取已有顺序约束，不在重写时擅自并发同一 journal 操作。
6. 同一份隔离数据先后运行旧、新客户端只读流程，比较安装实例 ID、候选、动作 DTO、订阅设置和事务 ID；关闭旧客户端后再测新端，避免双宿主调度干扰结果。

**产出：** 路径解析、一次性协议客户端、Dart 数据模型、协议样例测试、旧数据对比记录。

**退出条件：** Flutter 显示真实游戏库和来源数据；启动目录变化不影响资源定位；旧设置和记录可见；缺核心/协议失败/读取错误能明确显示，且没有重建空数据冒充成功。

## 五、P2：迁移任务宿主与应用关闭行为

**依赖：** P1。此阶段先建立任务通路，不依赖安装页面完成。

工作步骤：
1. 实现 `serve-task`：发送启动请求后保留 stdin，持续读取事件；处理 request_id、sequence、事件种类和最终响应。子进程归应用层持有，不能随着页面销毁而丢失句柄。
2. 实现取消：向 stdin 写 `cancel` 行，继续消费清理/恢复事件和最终结果；取消在进程尚未启动完成时也保留意图并在控制通道可写后送达。不把“已发送取消”视为“已取消”。
3. 按当前宿主迁移安装任务占用和来源任务标识/去重规则；同源更新、全库匹配、单实例重匹配的已有并发语义在第二节对应表列明后实现，不自行统一成一个串行队列。
4. 区分协议错误、进程异常退出、合法失败终态和正常慢任务。按真实退出/协议事实反馈；不加无进展计时器、不设任意任务截止时间。
5. 实现关闭协调：拦截关窗 → 停止新增调度 → 对所有活动任务请求取消 → 保持处理状态 → 任务清理终结后退出。遇到取消传输错误必须可见；仍待恢复的结果需持久记录或明确提示，不能直接报成功。
6. 使用现有 fixture 和可控假子进程验证事件与时序；再用隔离状态目录做真实来源任务取消验证。真实游戏写入取消留到 P5/P7。

**产出：** CoreTask、应用级任务持有、关闭协调和对应测试；协议/生命周期测试记录。

**退出条件：** 覆盖分块行读取、持续进度、事件之后的终态、启动时取消、重复取消、取消与完成竞争、无终态退出；换页不中断任务，退出不遗留正在写入的任务或 worker。假进程验证与真实核心证据分别标记。

## 六、P3：完成游戏库与补丁浏览界面

**依赖：** P1；可在 P2 完成前进行只读 UI，但不可提前开放安装。

工作步骤：
1. 建立页面壳：常驻游戏列表、内容区四栏目、全局来源入口、返回游戏上下文。页面只订阅应用状态，不创建第二套任务轮询。
2. 迁移共享展示函数的实际行为：本地化名称、matched/installed/attention 筛选、补丁归组、多镜像合并、来源线索区分。复用既有测试样例作跨语言对照，避免用名字/来源数重新发明匹配口径。
3. 默认 `matched`；保留手动筛选与搜索；首次扫描、刷新保留旧数据、没有安装游戏、没有筛选结果、来源尚未匹配分别显示。提供查看全部，但不自动修改筛选。
4. 完成概览与补丁管理的只读部分：来源/语言/DLC 条件优先，多个补丁/镜像才显示选择器，技术信息折叠。检查当前选择失效时的明确落点。
5. 迁移选择生命周期：换游戏进入概览；换补丁/镜像清除旧确认、ZIP 和预览；刷新仍有该实例时保留选择，实例消失时回到选择游戏状态。
6. 使用 Material 控件完成键盘焦点、长文本布局、最小窗口与缩放检查。

**产出：** 游戏库、概览、补丁详情、四栏目导航；展示层与选择行为测试。

**退出条件：** 用真实扫描数据完成查找→选择→查看条件；既有多补丁/镜像样例不丢条目；不能安装的线索不会呈现可用安装按钮；1180×760和850×560布局可操作。

## 七、P4：完整接入来源管理与自动匹配

**依赖：** P2、P3。

工作步骤：
1. 接入全局来源列表与启停/更新间隔/添加规则，单游戏订阅与语言偏好独立呈现。保存成功后采用返回 revision 并重读必要快照，不在 UI 自增版本号。
2. 对接 `update_source`、`match_games`、`rematch_game` 及取消，消费 source/match progress 和 update；对受影响实例使用 `project_instances` 更新安装能力，不每次都重扫全库。
3. 迁移新增游戏的自动匹配与到期来源调度。对照 `select_due_sources/source_scheduler_tick` 的实际条件，HGamer 补查源不当普通自动更新源。
4. 全局来源卡片默认折叠，多卡展开状态仅在当前会话保存；收起仍显示运行或失败摘要；折叠动作不发请求、不取消任务。
5. 更新失败、索引不完整、无匹配、补查命中分别显示；切换全局页与游戏页不丢运行任务。设置变化影响的提示就近展示。
6. 在隔离状态中修改订阅/间隔与添加规则验证，再检验真实来源读取/更新；明确记录网络失败与解析失败，不能用模拟返回替代真实接入证明。

**产出：** 全局来源页、游戏订阅页、任务摘要、自动匹配与调度。

**退出条件：** 冷启动、手动更新、单游戏匹配、全库匹配和取消均有明确结果；缓存/订阅变化正确反映到补丁动作；不因换页重复启动任务；来源折叠无业务副作用。

## 八、P5：闭合安装、结果、记录与恢复

**依赖：** P2 任务宿主、P3 补丁选择；不依赖整个 P4 完成。先用已有有效扫描/补丁结果完成安装闭环，P4 与 P5 均完成后补验“更新来源 → 匹配 → 安装”的联调。

工作步骤：
1. 将 actions.primary、automatic、local_archive、overwrite/reinstall 等 DTO 映射到 UI，沿用实际 operation。核对 release_id/selection_id 互斥、request_id 幂等、archive 和 cleanup_policy 等字段，不凭按钮文字构造核心动作。
2. 接入自动下载、本地 ZIP、覆盖安装、手动确认。候选/镜像切换撤销旧授权状态；选文件取消不误发安装；预览始终只读且不是前置门槛。
3. 点击后立即打开模态进度，显示真实阶段与可得计量；未知总量保持不定进度，阶段切换允许计数重置。运行时只允许取消，不允许通过遮罩隐藏。
4. 用真实 InstallerOutcome 呈现完成/取消/失败/仍需恢复。区分请求失败与安装后状态刷新失败；后者不推翻已收到的安装结果。
5. 结果关闭后恢复原页面焦点；记录页加载真实事务，失败信息完整可查。读取不到补丁名时保留标识，不编造时间或名称。
6. `recover` 保持全局范围：先列出全部受影响未完成操作，明确“恢复全部未完成操作”；执行后按各项实际结果更新，仍需恢复时不清除提示。
7. 先在临时测试目录验证真实核心安装/取消/恢复与文件结果，再在已明确范围的真实游戏上验收。没有授权或样本的项目标为待验，不冒充通过。

**产出：** 可运行的安装闭环、进度/结果对话框、记录与恢复页；文件级验证证据。

**退出条件：** 自动与本地路线可用，多镜像/手动确认有效；下载取消、写入取消、完成竞争和恢复失败可解释；成功后的文件及事务相符；应用关窗不会跳过必要清理；不引入新卸载功能。

**退出条件：** 没有 Flutter SDK、Node、Tauri 开发环境时可启动候选包；两类产物均找到核心与资源；升级后数据连续；CI路径正确；Release仍保持原命名规范。没有实际跑 CI 时只记本地通过。

## 十、P7：集中实机验收，切换入口，移除旧版

**依赖：** P0–P6 全部完成，并已记录阶段验证。

工作步骤：
1. 按下表检查已有证据，只补测缺项/新增改动，不无理由重跑已通过的验证。
2. 从候选包启动，完成真实游戏列表、来源、安装、结果、取消/恢复和关窗场景；125%/150% 缩放、最小窗口、长名称/路径/错误、鼠标与键盘检查分别记录。
3. 使用 overengineering-review 复核最终代码沿实际调用路径是否新增了无依据限制、兜底和任务抽象；这是专项检查，不能替代功能验收。

5. 确认 Decky 仍可构建、共享 Rust/协议未被误删，仓库不存在还指向 Windows Vite/Tauri 的有效入口。

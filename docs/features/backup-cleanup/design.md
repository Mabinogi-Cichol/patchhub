# 全部安装备份清理

日期：2026-10-15（Asia/Shanghai）。状态：**已实现并完成本地自动化验证；候选包已构建校验，实机验收待执行。**

关联：[施工记录](progress.md) · [现有缓存清理](../cache-cleanup/design.md) · [共享 Rust 安装器](../cross-platform-installer-migration/design.md)。

## 1. 目标与产品决策

用户要求在插件设置中追加安装备份清理，以释放非正常中止留下的备份占用；进一步明确“不需要区分，直接全清”，随后要求先制定计划。

清理范围是插件创建的全部安装备份。删除时不按 committed、failed、rolled_back、planned、applying 或 needs_recovery 等事务状态筛选，不按是否仍可恢复、是否有收据、备份年龄或任务归属决定保留；损坏/缺失事务记录不成为保留孤立备份的理由。用户主动执行后，原先依赖这些备份的恢复将无法完成，不把删除备份表述成恢复游戏。

计划阶段仅制定方案。2026-10-15 用户要求开始施工后，已实现核心、协议、桥接和设置 UI；设备部署与真实备份删除仍待实机验收。

## 2. 设置入口与交互

- 在全局设置的缓存页面追加“安装备份”区域，与“下载缓存”分别显示占用与按钮；保留已有路由以免旧入口失效，导航标题可改为“缓存与备份”。
- 显示全部备份的文件数和总大小，按钮“清理全部安装备份”。说明：“删除所有安装备份，包括中断任务留下的备份；清理后无法用这些备份恢复原文件。”
- 点击直接执行，不增加备份保留开关、事务分类列表、逐项勾选、审核流程或二次确认弹窗。
- 清理完成显示实际删除文件数/释放空间，并刷新占用；为空时显示无需清理。部分失败显示已删除的数量、空间和未删除原因，不把部分成功报为全清成功。
- 删除操作与安装、写入、回滚互斥，复用现有活动任务与共享锁；有进程正在使用文件时返回“安装任务进行中，请结束后重试”。这是操作时序约束，取得清理锁后仍删除所有事务状态的备份，不筛选需恢复事务。

## 3. 清理范围

| 项目 | 处理 |
| --- | --- |
| 当前 `<state>/installer/rust-v1/jobs/` 内的备份 | 全部删除，包括无事务记录/异常中断留下的备份 |
| 插件旧版 `<state>/jobs/` 及 publisher 事务 jobs 中的备份 | 纳入已确认的旧布局扫描，全部删除，避免历史残留遗漏 |
| 数字 `<index>.backup`、任务内 `backup/` | 删除文件及目录内容，不要求存在 journal |
| `.backup-cleanup-<规范 UUID>/` | 仅本备份清理器生成的隔离残留；纳入统计与重试，避免进程中止后漏扫。通用 `.cleanup-*` 不按备份处理 |
| `.stage` 暂存文件与安装包缓存 | 本功能不删除；下载缓存仍使用原按钮，备份清理不扩大为整个 jobs 目录删除 |
| journal/收据/authorization、任务与订阅设置 | 保留；不通过清空数据库掩盖中断或制造安装成功 |
| 游戏目录、存档、用户 Downloads、来源缓存和部署回滚包 | 不在安装备份清理范围内 |

`<state>` 在当前 Steam Deck 为 `/home/deck/.local/share/steam-patch-manager`。新 RPC 不接受用户传入删除路径。目录识别只限定插件创建备份的存储位置和实际布局，不给备份添加事务状态许可名单。路径链接不跟随到外部；无法访问的路径按实际失败报告。

## 4. 技术方案

1. 在共享 Rust 核心增加备份占用统计和全部备份清理服务。与 CacheService 的下载缓存职责分开；复用已有路径/句柄工具和互斥锁，不另建 Python 文件删除引擎。
2. 清理服务直接遍历已确认的当前与旧版备份根目录，不先按事务状态或数据库查询结果过滤。以实际成功删除统计文件数和释放字节；允许对剩余项重试，重复调用幂等。
3. 复用安装器写入/缓存的并发锁，并核对旧版事务存储的并发入口，确保统计后状态变化和后端并发 RPC 不导致删除正被复制的文件。前端禁用按钮不能代替核心互斥。
4. journal/收据保持可读。清理后若调用恢复而所需备份已删除，返回明确的备份缺失结果；不宣称已回滚、不依赖文件为空猜测安装成功。不添加清理前自动恢复、恢复审核或按状态保留的策略。
5. 在 CLI/protocol 增加对应 RPC（`backup_status` 与 `cleanup_backups`），返回占用/已删除/失败明细。更新生成的 Python/TS 合约，Decky bridge/main 仅转发与更新显示。
6. 前端分别保存备份占用和清理结果；避免套用现有“下载缓存已清理”文案。操作后刷新显示，不自动更改“安装成功后自动删除下载缓存”设置。
7. Windows 与 SteamOS 共用核心实现；不新增 Windows GUI 入口，本期产品入口为 Decky 全局设置。

## 6. 验收标准

- 同一调用删除所有当前/旧版备份，包括需恢复和无 journal 的备份，不依据状态跳过。
- 人工构造安装进程非正常结束后的残留，调用清理后备份占用为零；存在操作系统删除失败时准确报告残留而非假报成功。
- `.stage`、journal、收据、授权、下载包、来源缓存、游戏与存档保持原值；保留事务历史不等于保留备份内容。
- 与安装/回滚并发时清理不执行，任务结束后同一入口可全清；清理过程中不会同时进入写入。
- 缺失/损坏 journal 不妨碍扫描和删除孤立备份；再次清理为空并正常返回。
- 清理后恢复缺少原文件时明确失败，不标记恢复成功。设置页面显示真实释放空间并刷新，零占用/部分失败文案正确。
- 双平台核心与协议/bridge/UI 检查通过；实机只用本轮明确创建的测试备份验收，设备已有真实备份全清须在施工部署阶段明确实际执行范围。

本设计替代此前“仅清理已结束事务、保留待恢复备份”的新增功能思路。已有自动清理和历史缓存设计保留为背景；本功能的新按钮按用户决策全清。

## 7. 实现细节与当前自动策略

- 当前安装器只临时备份本次要覆盖的原文件。成功提交或成功回滚后自动清理该事务 `.stage` / `.backup`；异常中断、需恢复或删除失败可能留存。手动全清入口补充这些残留的清理，不改变自动安装策略，不提供长期卸载备份。
- `backup_status` 返回 `{total_bytes, files, failures}`；`cleanup_backups` 返回 `{status, removed_bytes, removed_files, failures}`。统计可能因不可访问路径不完整，UI 明确显示诊断。清理结果为 completed / partial / failed / busy；失败明细最多 512 条，超过时标注省略，不能据此宣称全清成功。
- 删除先持当前 CacheLock 独占锁，再在所有待扫描存储根下安全创建并持有固定 `journal.lock`，兼容旧事务写入者。已有 jobs 即使无锁文件也必须建锁，锁文件保留以避免后续进程锁到不同对象。全部锁取得后才开始删除；日志本体保持原值。
- 使用现有不跟随链接、拒绝重解析点/硬链接的文件句柄工具，扫描最多 100000 项、深度 128；达到边界返回失败明细，允许重试，不把不完整扫描报为零占用全清。
- Linux 删除前采用 `.backup-cleanup-<uuid>/item` 隔离并校验身份；统计和重试识别该专属布局。模糊 `.cleanup-*` 不删除，以免混入暂存。测试用真实子进程 SIGKILL 验证 rename 后中断仍可重试。
- 设置区域独立加载占用，操作后刷新；下载缓存自动清理偏好不变，不写新增持久化开关。原缓存路由保留，侧栏标题改为“缓存与备份”。

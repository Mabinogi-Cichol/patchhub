# 可导入脚本来源适配器设计

状态：**施工中，P0–P6 已实现并完成本地自动化，四个内置来源及通用表格全部脚本化；P7 本地发行与 Deck 部署/界面抽样通过，Windows 原生与实体手柄验收待执行**。施工拆分见 [implementation-plan.md](implementation-plan.md)，实际进度与验证见 [progress.md](progress.md)。已验证的运行时决策与接入合同见 [p0-contract.md](p0-contract.md)，全部来源的迁移清单见 [migration-matrix.md](migration-matrix.md)。

## 1. 目标与范围

不同网站需要不同的列表、表单、分页和详情解析逻辑。允许用户自行提供 Lua 脚本，在不重新编译 PatchHub 的情况下添加或更新来源；Windows 与 Steam Deck 使用同一套核心和同一份脚本。

本功能覆盖发行商索引采集、详情解析及按游戏查询的补查来源。**最终交付必须将全部内置来源迁移为脚本适配器**：Shiravune、Kagura 国内、Kagura 海外、HGamer 均使用与自定义来源相同的脚本 API 和执行器。迁移期间可分批切换，最终移除对应的 Rust 网站专用解析实现和分派，不保留脚本失败后回退 Rust 的双轨路径。核心继续负责网络边界、身份匹配、缓存、补丁选择、下载和安装，脚本负责提取网站事实。

本期不做脚本市场、订阅远端脚本更新、签名发行平台、多脚本依赖系统、浏览器自动化、登录/验证码绕过、原生动态库加载或多语言运行时。需要执行网站 JavaScript 才能获得数据的网站不由本期承诺支持。

## 3. 运行时与信任边界

### 3.1 技术选择

使用 **Lua 5.4 + Rust `mlua`，随核心静态构建**。P0 已锁定 `mlua 0.12.2` 的 `lua54/vendored/serialize`，实际编译 Lua 5.4.9；仓库 Rust 1.94 的 Windows MSVC 与 WSL Ubuntu 原型均通过。P1 将 `mlua` 移为核心依赖用于导入语法检查；P2 将原型执行器迁入 [script.rs](../../../crates/core/src/sources/adapters/script.rs)，提供列表、详情及补查事实的类型化入口，原型回归迁入同一实现的单元测试。P3 已接入发行商生产调度，正式发行包仍待 P7 核验；目标是用户无需安装 Lua、Python 或 Node。Steam Deck 设备与正式发行构建不能由 WSL 测试代替。

每次采集/详情/查询调用创建独立 Lua 环境，不跨来源共享可变全局状态，不建立运行时池或常驻脚本服务。长任务通过现有任务通道运行。

### 3.2 明确支持的信任范围

第一版面向用户**主动导入并信任的脚本**，不自动从网站下载执行脚本，也不宣称能隔离任意恶意代码造成的内存耗尽或解释器缺陷。导入页面需简短说明脚本会执行来源解析逻辑以及允许访问的域名。

即使是主动导入的脚本，也不应获得与来源解析无关的主机能力：

- 显式选择所需基础函数及 `string`、`table`、`math`、`utf8`；不直接使用“全部安全标准库”作为业务权限策略。
- 不开放 `io`、`os`、`package`、`debug`、FFI、原生模块、`require`、`dofile`、`loadfile`；不向脚本提供文件系统、进程、环境变量、游戏目录、安装器对象或原生指针。
- 只加载 Lua 源文本。模块加载与调用均接入现有取消信号；模块顶层的纯计算循环也必须可取消。
- 使用 VM hook 检查用户取消，使用同一个网络上下文处理在途请求取消。hook 的采样间隔是取消响应的实现参数，不是正常任务的指令总数上限。
- 取消标志一旦成立，Rust 在入口返回及发布结果前仍检查该标志；脚本用 `pcall` 捕获宿主错误不能把已取消任务改写为成功。受保护调用中的循环取消行为也需 P0 验证。
- P0 已确认：只用 hook yield 不能覆盖 C 标准库回调内的受保护循环。实际方案为 hook 报错与受控 `pcall/xpcall` 调用前后取消检查，原始受保护函数不暴露给脚本；详见 [取消合同](p0-contract.md#取消合同)。不通过异常吞掉取消，也不新增任务总时长限制。
- 不预设脚本大小、条目数、页数或任务总时长上限，不为脚本另加 TTL、看门狗、失败自动重试或超时框架。C 标准库长调用与实际内存占用的限制需在 P0 实测并如实记录；不可用“已沙箱化”掩盖未覆盖边界。

以上能力限制对应真实边界：导入的是可执行代码，而需求仅为读取来源网页并提取事实。将来若要自动执行未经用户信任的第三方脚本，需另行设计和验证更强的进程/资源隔离，本期不提前建设。

## 4. 导入、存储和替换

### 4.1 用户输入

作者可分别维护 `source.json` 与 `adapter.lua`。第一版两端共同提供“来源规则 JSON + Lua 源码”导入编辑器，支持粘贴、示例与复制；不要求先有 ZIP 来源包格式或 Decky 远端文件浏览器。Windows 文件选择可作为同一编辑器的文本读取辅助，不向 Rust/Decky 增加任意文件路径执行接口。

来源规则继续描述 ID、名称、角色、页面与下载域名，新增适配器类型暂定 `lua`。脚本 API 版本在导入请求中单独声明，不混同客户端 JSONL 协议版本。配置中不保存作者电脑的脚本绝对路径。

新增接口拟为：

| 接口 | 语义 |
| --- | --- |
| `import_script_source(rule, api_version, code, replace=false)` | 校验规则与源码语法，计算摘要，原子保存规则和代码；`replace=false` 遇到同 ID 报错；`replace=true` 只显式更新已有脚本来源 |
| `get_script_source(source_id)` | 仅在编辑时返回脚本规则和源码；普通来源列表与游戏快照不携带整段源码 |

不允许该导入接口悄悄覆盖已有来源。内置来源迁移为脚本后，`get_script_source` 可读取其有效脚本，用户通过显式 `replace=true` 保存同 ID 的用户覆盖；沿用现有规则覆盖模型，发行版更新不覆盖用户已保存的脚本。迁移前的 Rust 来源不能被当作已具备脚本描述的来源直接替换。原 `add_source` 继续服务现有声明式规则，不能通过填 `adapter=lua` 绕过脚本导入校验。

导入只做数据和语法检查，**不执行模块顶层、不抓取网站**；缺失入口或运行时异常在实际可取消任务中明确报告。“语法检查通过”不代表来源链路验证通过。是否启用沿用规则 `enabled` 与现有开关，不新增二次激活状态。

### 4.2 最小持久化方案

- 在现有来源设置中增加默认空的脚本源码映射，按来源 ID 保存；规则中的可选脚本描述包含 API 版本与核心计算的源码 SHA-256。
- P1 设置文件使用独立的 `SOURCE_SETTINGS_SCHEMA_VERSION=3`，读写打开时一次升级 v1/v2 并保留各设置字段及 revision；只读打开接受 v1–v3，不执行升级。来源命名空间 `schema.json` 仍为 v2，现有索引/详情/匹配格式保持原版本，不因设置升级重新执行旧缓存迁移。旧二进制不能读取 v3 设置，降级兼容不在承诺范围内。
- 源码、规则、摘要与设置版本通过**同一次设置写入**提交，避免规则已经更新而脚本文件仍是旧版本。复用现有锁、原子替换与错误传播，P1 必须验证提交确实覆盖完整设置事务，不能只连续修改两个内存字段后宣称原子。
- P1 已统一为锁内读取最新完整设置、编辑副本、一次原子保存、成功后发布内存快照；启用、名称、订阅、普通来源添加和间隔写入使用同一事务，移除旧 `apply_overrides/bump_revision` 分步链路，避免旧进程覆盖新导入的脚本和其他用户设置。
- 仅新增字段的阶段不向旧规则输出空脚本字段，避免无关指纹变化；旧设置没有源码映射时按空处理。内置来源实际切换到脚本时，其有效描述必须包含 API 版本与摘要并相应改变解析身份，按 §6.2 处理旧缓存/选择，不能承诺跨执行引擎仍保持旧指纹。
- 替换同一脚本来源时保留用户名称覆盖、启用状态、游戏订阅和更新间隔。角色变化按现有角色调度语义处理，不丢弃用户设置。
- 同一次来源任务捕获同一份规则与源码快照，计算时不重新读取作者文件。发现存储摘要与源码不一致时报告该来源错误，不能退回旧脚本或某个内置适配器。
- 本期复用“停用来源”停止使用脚本；不新增脚本商店、历史版本库、后台更新器或清理服务。

## 5. 脚本 API v1

P0 后的接口名称、DTO 字段与宿主值转换规则见 [API 合同](p0-contract.md)。以下仍是生产接入目标，不能当作客户端已支持的 API。

| 脚本入口 | 使用场景 | 返回事实 |
| --- | --- | --- |
| `collect_index(ctx, rule, previous)` | 发行商列表/目录采集 | 索引条目、完整性、剩余页面与条件请求信息，对接 `IndexOutcome` |
| `resolve_page(ctx, rule, page)` | 列表只包含详情链接 | 与查询无关的 `PageFact`，包含 Steam ID、标题、镜像、正文和必要的后续链接 |
| `discover(ctx, rule, query, previous)` | 按游戏搜索的补查源 | 页面事实及本次查询的完整性/诊断，由核心生成候选 |

发行商必须有索引入口；仅产生直链 `entry` 的脚本无需详情入口。补查源必须有查询入口，不参与全站索引定时更新。索引返回详情条目却缺少解析入口应报告合同错误，不返回伪成功空结果。

`ctx` 只暴露当前需求所需能力：

- 受 `page_hosts` 约束的 GET/POST、表单提交、响应状态/文本/最终 URL，复用当前 Cookie、编码和重定向处理；不提供自动继承用户浏览器凭据的接口。
- HTML CSS 选择、节点文本/属性、相对 URL 合并和 JSON 编解码。优先复用现有 `scraper` 与 URL 处理，不另建网页选择器 DSL 或脚本专用 HTML 引擎。
- 任务进度与取消检查；进度的源 ID、设置版本等核心字段由宿主填入，脚本不能任意指定。

脚本输出在 Lua/Rust 边界做一次类型与业务校验，然后复用现有标准化、身份判定及候选生成。候选 ID、指纹、选择 ID、可安装能力、安装许可和事务状态不由脚本直接声明。脚本给出的下载地址继续受 `download_hosts`、下载验证及现有安装流程约束。

采集沿用 `complete/pending` 语义。返回有效部分结果时可保存既有形状的续跑数据；脚本异常未返回结果时，保留上次正式索引及已有进度并报告失败，不承诺恢复 Lua 局部变量。网络/解析错误不得吞成“确认没有补丁”。本期不为表单状态发明通用持久化协程或执行恢复框架；确需新增续跑字段时先用真实样例证明现有形状不足。

## 6. 核心调度、缓存与安装一致性

### 6.1 统一分派

P3 已将 `SourceAdapter` 接入 `update_source` 和发行商详情匹配，P4 接入补查发现。Lua 与临时保留的 Rust 实现由同一入口分派。公共详情接口返回既有 `PageFact`，分类内联、链接与分页复用同一遍历；不把 Lua 条目交给 Kagura 解析。分阶段接入时 Rust Kagura 通过该入口委托；P6 将其网站解析逻辑移入 Lua 并删除该临时 Rust 委托。仅保留实际被多来源使用的 Rust 基础能力，不把网站专用算法藏入通用宿主回调。

更新/匹配入口和 CLI 均传递拥有生命周期的同一 `Arc<AtomicBool>`，直接调用核心时也建立同一取消作用域；Lua hook 与网络等待观察同一标志。任务使用捕获设置中的源码并验证其摘要。开始执行/复用前及提交前检查已保存定义是否改变；跨进程替换时拒绝发布旧索引，旧匹配文件保留但不能作为新规则的成功结果返回。

只读扫描、投影、预览、列表和能力查询不得因加载脚本元数据而运行 Lua 或联网。实际脚本仅在明确的来源更新、游戏匹配/重匹配任务内执行。

### 6.2 脚本替换必须影响真实消费者

规则指纹纳入脚本 API 版本与源码摘要；每次任务使用摘要匹配的源码。仅修改脚本同样属于解析逻辑变化，不能只增加 `settings_revision`：

1. 脚本索引记录其产生时的有效解析标识；更新后的规则与旧索引不匹配时，旧文件保留，但该来源表现为待更新，不将旧候选投影成当前可安装结果。
2. 索引内容修订将脚本解析标识纳入变化判断，使“条目字面相同但解析代码已变”也能触发现有详情/匹配修订检查。尚未切换的来源不因新增脚本能力发生无关修订；实际迁移的来源必须按新解析身份重新取得可用缓存。
3. 详情缓存、游戏匹配缓存、`cached_candidates`、`cached_discovery`、只读快照、ZIP/EXE 和手动选择重新解析均需检查所用结果与当前脚本/规则相容；不能只修更新入口而让读取或安装继续使用旧结果。
4. 旧选择 ID 在新规则下不能被当作当前授权；使用现有过期/重新匹配错误语义。用户名称编辑不改变脚本解析标识。

P3 给 `SourceIndex` 增加可选 `parser_fingerprint`，脚本来源写入含 API/源码摘要的规则指纹，旧 Rust 来源缺省/省略。发布比较解析指纹与内容；脚本变化时即使条目相同也沿旧正式索引递增修订，详情继续用已有 `index_revision` 失效。旧索引和进度若解析身份不符则不供复用，但保留原文件；不进行全库清理或无关迁移。

仅有索引修订不能使“相同网页事实产生的旧选择 ID”失效，因此 `SourceCandidate` 也增加同一个可选 `parser_fingerprint`，由核心生成。脚本候选 ID 由原候选 ID 和解析指纹共同生成，候选指纹覆盖该字段；ZIP/EXE 选择绑定纳入该指纹，人工选择/手动 URL 继续绑定实际候选身份。未脚本化来源省略字段，原候选/选择 ID 和现有夹具保持。该字段同步生成 TS/Python/schema 与 Flutter 资源；不是另一套独立代际。

缓存直接读取、来源/游戏列表、匹配摘要和只读快照复用共同的解析相容性检查，移除旧脚本结果后重新投影状态。安装 ZIP/EXE/人工选择与手动 URL 均从该有效候选视图重新解析，不执行 Lua。设置 schema 3、命名空间 2、索引/详情/匹配 1 保持：新增字段缺省为空，仅脚本结果写入；旧脚本无标识缓存须重新更新，旧文件保留。无新增 TTL、租约或每种 DTO 的独立修订。

### 6.3 多个补查来源

P4 复用一份 `FallbackMatchRecord` 承载聚合结果，不增加每源记录数据库。调度从只取一个补查源改为按优先级、ID 顺序遍历全部启用且被当前游戏订阅的补查源：

- 查询缓存键覆盖游戏查询与按来源 ID 排序的全部参与规则/脚本摘要；任一来源变化即使聚合查询失效。
- 候选按原来源 ID 标记并通过现有身份合并；一个来源失败不得删除其他来源本次成功的结果。
- 至少一个可信候选可以报告补查命中，同时保留失败来源诊断；只有所有参与来源均完整成功且无候选才能报告无结果，其余沿用未完成/失败语义。
- 保持普通发行商可信命中优先的现有规则。HGamer 在过渡阶段可保留 Rust 实现，最终必须切换为脚本并参与同一分派与聚合。
- 补查键形状更新可能使旧聚合记录在下一次匹配重算一次；保留历史文件，不将旧单源负结果复用于新来源集合，不扩大为全库缓存清理。

Lua `discover` 的页面事实与内联事实进入公共候选生成；身份事实只用于当前 AppID 的别名补全，其他游戏身份不能授权当前游戏。来源 ID、候选 ID/指纹、镜像格式和解析指纹均由核心生成，脚本不能直接声明候选权限。保留本次成功来源的候选及各来源完整诊断；全部失败的聚合为 `Failed`，部分完成/仅有线索为 `Incomplete`，整场游戏状态仍沿原发行商覆盖规则推导。正常匹配可以复用已有可信命中；显式重新匹配强制查询全部参与源。

完整查询键覆盖 AppID、游戏名、名称提示和来源集合指纹；集合指纹由按 ID 排序的规则/脚本摘要与解析版本生成，不依赖规则输入顺序。只读投影拿不到原前端名称提示，不能仅靠完整查询键核对当前来源集合，因此聚合记录新增可选 `sources_fingerprint`。普通读取、冻结快照及安装候选读取只比对当前启用/订阅集合的这个摘要，不执行脚本。来源增删、启用/订阅或源码变化后，旧聚合暂不展示，重新匹配生成有效结果；旧无绑定记录也需重新匹配。存储 schema 保持，旧文件保留，无新 wire 字段或全库迁移。

补查继续沿现有调度条件：有启用且订阅的发行商，且其索引覆盖完整时执行；发行商可信命中优先，覆盖未完成时不把补查变成绕过索引的全库网络任务。“仅脚本/仅 HGamer”验证指补查集合只有该类来源，未改变这些覆盖语义。补查源不接受全站更新或定时索引间隔；导入与编辑的客户端入口仍归 P5。

## 7. 内置来源全面迁移与旧实现退役

全部内置来源是本功能的必验对象，不能只完成一个示例或开放自定义导入就标记完成：

| 来源 | 必须迁移并保持的行为 |
| --- | --- |
| Shiravune（`patchmoe`） | 语言表单、Cookie/跳转、双语列表、直链条目与发布日期提取 |
| Kagura 国内（`kagura-cn`） | 列表分页、文章/分类详情、Steam ID、正文与镜像提取，以及已有本体/DLC 关联行为 |
| Kagura 海外（`kagura-en`） | 多入口目录、产品/分类分页、详情与镜像解析，以及已有匹配和变体行为 |
| HGamer（`hgamer`） | 按游戏搜索、身份线索、上游页面/链接提取及完整/部分/失败结果 |

通用 `table_html` 也改为随包提供的 Lua 适配器，继续读取现有 `columns/table_id` JSON 配置，避免保留另一套网站解析执行路径。Rust 可继续提供 HTML DOM、HTTP、URL、编码与统一身份算法；不保留只服务单个网站的宿主函数来变相维持旧实现。

内置脚本作为发行资源纳入 Git，并随核心打包或编译内嵌；两端不依赖用户额外导入它们。它们与用户脚本采用同一 API、权限边界、取消、摘要和错误处理流程，区别只在代码来源。构建与读取时由核心生成有效脚本描述，普通扫描不执行代码。

P6 实际资源位于 `crates/core/resources/source-scripts/`，由 `sources/builtin.rs` 编译内嵌。公共 Lua 文本与站点代码组成完整可读取源码，采用 LF 与原始字节 SHA-256；旧 adapter 名仅作资源定位，不保留 Rust 网站执行分支。读取输出 `adapter=lua` 的作者规则供显式同 ID 覆盖，名称、启用、订阅、间隔继续使用原设置。公共宿主仅补 DOM 直接子元素和 URL、日期、身份/单词算法，详见 [API 合同](p0-contract.md#ctx-与-dom)；网站选择器、表单、分页和正文提取全部位于 Lua。


保留四个来源 ID，延续名称覆盖、启用状态、订阅和间隔。现有公开 `adapter` 名称若需兼容，映射到随包 Lua 脚本；该映射只定位脚本，不执行旧 Rust 解析，也不根据失败在新旧引擎之间切换。迁移导致的有效解析身份变化按 §6.2 显式处理。

逐源完成生产分派下的脚本验证后，删除对应 Rust 网站模块、注册/详情分支及仅服务已删除路径的代码；将仍验证业务合同的夹具/测试迁到脚本调用链。最终验收检查生产代码和发行包，不允许旧 Rust 路径因“便于比较”永久保留。迁移期对比证据可保存于测试记录，无需随产品保留双实现。

## 8. 双端集成与兼容

- Windows、Decky 都只编辑和传递规则/源码文本，运行统一位于 Rust 核心；不在 Flutter、浏览器或 Decky Python 中解释 Lua。
- 增加导入、编辑、显式替换、示例与错误展示。来源卡片显示脚本类型/API 版本/摘要供核对，不在游戏流程中展示整段脚本。两端均使用规则 JSON、API 版本、源码三个有标签的输入；编辑时显式读取，替换绑定到原 ID，查看/复制示例不覆盖草稿。
- 现有来源名称编辑、启用、逐游戏订阅、更新间隔、任务进度和取消继续使用现有接口。
- 同步 Rust 协议定义、`contract-gen` 产物、跨语言夹具、Python 桥接、TypeScript 及 Flutter 方法表/schema。当前客户端严格比较能力方法表，不能只增加 Rust 方法而不更新两端。
- 新源码输入不沿用 Decky `add_source` 文本入口的固定长度限制；不为传输另设无依据的源码上限。普通扫描结果只携带描述，不反复携带整段代码。
- JSONL 保持 v5，Lua API v1 独立版本化。方法表增加 `import_script_source/get_script_source`，能力新增 `sources.script_api_version=1`；旧核心与新客户端组合明确报能力不兼容，不自动走另一套执行路径。
- 保存回执与来源/游戏投影刷新分开处理，刷新失败显示已保存；保存不执行 Lua。成功保存先丢弃 UI 旧来源候选和动态补丁，再从核心投影，避免原“失败时保留结果”逻辑恢复旧脚本选择。签名目录条目保留，不增加客户端解析身份缓存。

## 9. 验收与遗留风险

必须覆盖两端同一脚本导入、重启保持、实际列表/详情/查询、取消、源码替换后的缓存及安装选择失效，以及全部内置来源迁移后的行为等价和旧 Rust 网站实现退役。全部来源迁移、逐源证据和双端发行资源齐全是最终交付条件，不能以单站点样例替代。详细用例和阶段出口见 [施工计划](implementation-plan.md)。

P0 已验证双平台原型构建、宿主回调作用域、DOM 生命周期、受保护循环取消、值转换及 Kagura 海外录制样例；长 C 调用只能返回后检查取消，资源占用测量见 [P0 合同](p0-contract.md)。P1 已验证导入/读取、设置事务、并发/失败、重启及只读快照。P2 已验证同一核心执行器的事实校验、宿主绑定进度、完整结构化错误和取消；实际网络等待响应头/正文的取消复用安装下载的异步等待机制，不增加任务总时长限制。P3 已覆盖发行商更新、共享详情、分类分页及缓存/选择重解析，P4 覆盖多源补查与聚合读取失效，最终平台验证见施工记录。P6 已完成逐源离线对照与只读网站抽样验证；各站全量实时目录、正式发行包、两端实机输入与实际游戏安装行为仍待 P7 验证。运行时接口限制不等于已证明的恶意代码资源隔离；脚本能声称网页上不存在的事实，结构校验不能证明作者或网站可信。

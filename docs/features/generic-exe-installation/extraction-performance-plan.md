# 提取性能修复计划：移除逐块缓存身份复查

日期：2026-11-09（Asia/Shanghai）。状态：**已实现，双平台定向验证及 Windows 隔离性能/样本回归通过；已安装应用、真实游戏和设备验收未执行。实际结果见[施工记录](progress.md#2026-11-09提取性能修复实施与验证)。**

关联：[设计](design.md) · [施工记录](progress.md) · [单一纯解压方案](archive-extraction-plan.md)。开发分支：`fix/archive-extraction-performance`，从已合并单一纯解压功能的 `main` 创建。

## 1. 问题与证据

用户在 Windows PatchHub 0.6.0 为同级生 Remake（AppID 1689910）安装 ZIP 补丁时报告提取慢。正式 journal / requests 数据库以只读方式查询：事务 `72d17032-08bb-4d7e-b79f-8c40ba358fed` 最终 committed，2026-11-08 23:43:47 创建、23:47:16 提交，约 209 秒；3 个输出文件共 1,563,269,624 字节。此前请求阶段约 126 秒，没有逐阶段持久日志，不能归入提取或进一步精确分解。

缓存包为 `dokyusei-remake-dlc-en-zh_Windows_1_1_0.zip`，SHA-256 `d006bd8b1f0eb0d7e95503cdef7cbcb79bba48704a79389bf22ee8db99c20103`。缓存在 C 盘 NVMe SSD，游戏在 F 盘 SATA HDD。没有做 F 盘写入基准，不能把剩余耗时全部归因于机械盘。

基线 HEAD `f21d1a7f47b96d7a29ab7197655b4838f04b7ec6` 的相关 ZIP/service/cache_lock 文件与本地 v0.6.0 tag 无差异。现有源码实际路径：

`service::install → operation::with_safety(CacheLock::validate) → zip_direct::extract → 每次 read 前 check(cancel) → operation::check → safety → CacheLock::validate`。

256 KiB 是输出缓冲区容量，不是每次 read 的实际返回大小。本包通常返回约 8–9 KiB，完整只读提取共调用 read 171,254 次（包含 EOF），每轮都会重新打开、核对 8 层目录锚点及锁文件。

已完成的调查测量，不代表修复验收：

| 测量 | 结果与边界 |
| --- | --- |
| 复用产品 ZIP 读取源码、现有 release ZIP 和匹配 release profile 的 SHA-256 依赖；省略写盘及安全回调 | 全包解压、CRC、SHA-256 合计约 5.9 秒，摘要与正式记录一致 |
| 复用真实 CacheLock::validate，每次 read 前调用；两个大文件各只读前约 32 MiB | update.arc：3,523 次、3.403 秒；voice2.arc：4,050 次、4.631 秒；read 与 SHA 分别仅约 0.145 / 0.148 秒，约 96–97% 时间为校验等额外开销 |
| 按各文件完整 read 次数外推 | 校验约 163 秒；属于抽样外推，不能当作原安装分段实测 |

原始调查及基准源文件保存在本地 [.artifacts/extraction-investigation](../../../.artifacts/extraction-investigation/findings.md)，该目录是本地辅助材料，不作为文档可用性的唯一依据。较早使用不同 SHA 依赖 profile 的探索基准不用于正式性能对比。

## 2. 产品决策与范围

1. 删除安装字节处理循环中的完整缓存身份复查，不改成 TTL、定时检查、每文件复查、重试或用户配置。
2. 安装与清理的冲突在操作开始时处理：沿用共享/独占锁，取锁失败立即返回既有 `installer_busy`，执行期间持锁，不等待轮询、不进入提取后再处理冲突。
3. Windows 安装请求启用成功后自动缓存清理：自动安装与手动下载两个入口均将 `cleanup_policy=disabled` 改为 `after_commit`。复用核心现有 AfterCommit 流程，在本次安装持久提交成功、释放共享锁后再尝试独占锁清理。清理仍属于当前安装任务，进度窗和忙碌状态保持到最终结果返回；不另起后台任务或增加开关、调度器。若实施时发现已有其他真实可并发清理入口，仅复用其正在运行状态禁用安装。
4. 不把同 UID 外部进程任意替换状态祖先作为本次安装热路径持续检测的目标。既有锁获取边界、Windows 禁止 DELETE 共享的目录/锁句柄、Linux 原目录与锁文件的双锁继续沿用；不声称可隔离任意同用户恶意修改。
5. 保留真实路径边界、输出普通文件/链接检查、实际 I/O 错误、CRC/摘要、写入取消与完成语义。辅助缓存路径身份复查和压缩包内容校验是两件事，不删除后者。

## 3. 最小代码修改

### 3.1 安装入口和操作控制

- 在 [service.rs](../../../crates/core/src/installer/service.rs) 移除 `safety_guard` 克隆及 `operation::with_safety` 包装。共享锁从获取成功一直持有到安装执行结束；清理前仍显式释放共享锁，再按原规则尝试独占锁。
- 在 [operation.rs](../../../crates/core/src/operation.rs) 删除只服务于该包装的 `safety` 字段、初始化、`with_safety`、恢复旧回调的辅助代码，以及 `check()` 中执行 safety 的分支。当前只有安装入口使用该回调；施工时复核调用方，清理相应失效注释和专属测试。
- `operation::check()` 的取消语义、现有其他 gate 契约不改变。本次不借机扩展成全部操作控制层清理。
- 同时覆盖 ZIP、EXE、签名安装经过该公共入口的路径，避免仅在 ZIP 内绕过检查而留下同一问题。

### 3.2 锁与文件操作边界

- 不删除 CacheLock 本身；取锁前后的一次性身份核对、安装/清理互斥、句柄生命周期与 Drop 释放继续沿用。
- `recover` / `discard_plan` 的操作边界复查及清理服务的删除边界复查没有本次高频解压调用，不在本次修改范围。保留 `CacheLock::validate`，不因删除热路径回调就误删其他调用和测试。
- 不为取消检查增加新的文件系统查询，不将移除的完整验证迁移到 `advance`、进度上报或解压回调中。
- 不同时调整缓冲区、EntryReader seek、并行解压、摘要算法或 sync_all。Windows 自动清理仅改变请求策略，沿用既有核心清理范围；性能比较分开记录提取与提交后清理耗时。

### 3.3 Windows 安装成功后自动清理

- 修改 [patch_management_page.dart](../../../apps/windows-flutter/lib/pages/patch_management_page.dart) 的自动安装与手动下载请求，统一传入 `cleanup_policy: after_commit`。Decky 沿用已有用户偏好，本次不改动。
- 核心仍只对本次新 committed 的安装执行清理；失败、取消及同请求重放不触发。清理忙碌或失败单独展示在既有 cleanup 结果中，安装成功保持成功，不回滚、不重试。
- 沿用核心缓存删除范围和保留规则，不删除游戏文件、事务记录或仍被使用/需要保留的材料。安装前及提取期间不清理；已有最终结果界面展示清理失败，无需新增中间确认。

## 4. 实施与验证顺序

1. 保留现有调查证据；在本分支修改上述公共入口与专用回调，沿调用路径核对不再逐块重开缓存祖先和锁文件。
2. 运行受影响核心路径的既有定向测试：ZIP/EXE 直接提取、公共安装服务、签名安装、进度取消、缓存跨进程互斥及 AfterCommit 清理。核对清理持独占锁时安装在写游戏前拒绝、安装持共享锁时清理拒绝、终态后释放锁。优先复用现有测试，只有业务行为覆盖缺口才补测，不增加只断言某个内部函数被删除的测试。
3. 补充 Flutter 定向验证：自动安装与手动下载请求均传 `after_commit`；清理阶段进度窗和安装忙碌状态持续，最终结果可展示安装成功及独立清理失败。复用核心 AfterCommit 回归验证新提交触发、失败/取消/重放不触发，以及独占锁忙碌不改写安装成功。对涉及 Dart 文件执行格式检查和受影响安装流程测试。对 Rust 修改执行 `cargo fmt --all -- --check`、受影响 core 包 Clippy（`--all-targets --locked -- -D warnings`）；若清理导致 CLI/worker 接口或生成物实际变化，再补相应检查。日常修复不运行发布前完整 CI matrix。
4. Windows 为主要复现平台；共享 Rust 入口也服务 Linux，故 WSL Linux 定向复跑取消、互斥和受影响安装测试，核对移除回调后双平台契约，而非执行完整 Linux 发布 job。各平台使用各自工具链和输出目录。
5. 性能比较使用修改前后相同 release 构建条件、同一个缓存包、同一隔离输出磁盘和目录布局，直接走生产安装服务提取路径；记录提取阶段、前置/提交阶段、提交后清理阶段耗时、文件数、总字节和每文件摘要；提取性能对比使用相同清理策略，Windows 新默认策略另做端到端确认，避免清理耗时掩盖提取收益。正式下载缓存只读作为输入，运行状态和输出放在独立 `.artifacts/` 子目录，不写真实游戏。已有生产提取验收入口可复用，计时只作为本地验证辅助，不新增产品遥测框架。
6. 再用一个现存 EXE 样本走同一公共入口，确认解压、摘要、进度和取消正常；样本先核实存在，不把历史文件路径当作现存材料。
7. 按 overengineering-review 对最终实现复核，更新本功能施工记录中的实际命令、基线、结果、日志和待验证项；发现新增修改或失败后仅重跑相关检查。

## 5. 验收标准

- 下载、哈希、ZIP/EXE 字节读取/写入的逐块检查不再重新打开整个缓存路径；取消仍能在数据块边界生效，写入期间取消返回未完成语义，已持久提交成功后到达的取消仍沿用成功优先契约，不恢复覆盖新文件的旧流程。
- 同一补丁仍输出完整 3 个文件，大小、摘要与原记录一致；没有组件筛选、临时搬运、额外回读或新增硬限制。
- 安装/清理冲突在操作入口明确返回，任务完成后锁释放；不会删除正在使用的缓存，不依赖热路径身份复查实现互斥。
- Windows 自动安装与手动下载均启用 `after_commit`；清理完成前任务仍忙碌，失败/取消/重放不自动清理，清理失败或忙碌不改变安装成功结果。
- release 生产服务对比确认删除了此前占主导的复查开销，并记录实际提取耗时。5.9 秒是不写盘的调查对照，不作为真实写盘安装的承诺或硬门槛；结果不能用其他依赖 profile、调试构建或不同磁盘直接替代。
- 自动化通过、本地性能验证、已安装 Windows 应用验收和 Steam Deck 实机验证分别记录。此次计划阶段均不宣称修复通过；更新已安装应用、部署设备、写入真实游戏、提交、合并和发布不属于本轮计划编写操作。

## 6. 计划精简审阅

已按 overengineering-review 沿公共安装入口、operation 回调、直接提取和缓存锁获取/释放路径审阅。结论：本方案可实施；直接删除已确认昂贵的逐块包装及专用状态，保留实际互斥和文件边界；不以更大缓冲、计时阈值或新检查层替代删除。Windows 自动清理直接复用现有 AfterCommit 契约，新增范围仅为两个请求参数及相应验证，不增加后台状态机。剩余磁盘耗时占比与实际修复收益需要实施后的相同条件对比，不能将抽样估算写成验收结果。此段保留计划阶段审阅结论；最终代码复核已完成，范围与实际验证见施工记录。
